## TL;DR

- On **LongMemEval** (long-context memory benchmark, ~104k-token haystacks), **Headroom's default content router compresses the context by ~55% *and* improves end-to-end answer quality**. On the N=50 headline slice it beats the uncompressed baseline by **+22 percentage points** (74.0% vs 52.0%) while cutting p50 latency from 7.1s to 4.4s.
- The gain **generalises across 5 of 6 LongMemEval question types** (per-type N=30 sweep). Cross-type grand means: baseline 30.3% → **headroom_default 50.1% (+19.8pp)** → summary_prompt 36.7% (+6.3pp), at 55.1% / 39.5% compression and 5,461 ms / 9,459 ms p50 latency respectively. The only per-type exception is `temporal-reasoning`, where all arms collapse to ~0% — a Sonnet 4.5 long-context weakness, not a Headroom problem.
- **All errors in the sweep are Anthropic 429 rate-limit errors on the baseline arm** (baseline sends full ~110k-token haystacks → burns the 2M TPM org cap; Headroom and summary_prompt have zero errors). The rate-limit pattern is itself a compression story: at org-level TPM budgets, compression is what lets the workload run concurrently. Reported baseline quality is on a successfully-completed subset, so the true Headroom Δ is at least as large as reported, very likely larger.
- A custom summarization prompt ("Feature A" — Haiku 4.5 structured JSON) achieves ~40% compression with weakly-positive average quality (+6.3pp grand mean). It is **dominated by Headroom on 5 of 6 types** with its current SWE/planning schema but is the *only* arm that clears 0% on `temporal-reasoning`. Not a dead end; a schema redesign for conversational tasks might flip the verdict.
- The RES-333 framing assumed that both OpenAI and Anthropic ship summarization-based compaction at the standard API level. **They don't.** The closest mechanisms are either lossy (`truncation="auto"`, `clear_tool_uses`), scoped to tool-calling loops (`tool_runner(compaction_control=...)`), or purely analytical (`responses.compact()` is an inspection endpoint whose result ID is not chainable). Both provider arms were dropped from the headline comparison after smoke runs exposed architectural dead-ends; this itself is a noteworthy finding — it strengthens the case that there is a real market gap for a Headroom-like compression layer.
- **Recommendation:** Ship Headroom behind a feature flag for long-context memory / RAG workloads. Do not ship Feature A as-is (schema-shaped for SWE/planning, not conversational recall). Open a Phase 2 workstream for (1) re-run on orq production traces after Karina's JSON-unwrapping fix lands, (2) a second model, (3) τ-bench (agentic tool-use), and (4) LongBench v1 (LLMLingua-2 head-to-head).

## 1. Background

The Apr 7 sync assigned Headroom evaluation ownership to Arian with a one-week deadline. Bauke's literal ask on RES-333:

> Baseline: uncompressed long document (perhaps longmemeval + long context agentic dataset). Compare with: openai compaction, anthropic compaction, headroom compaction, custom summary prompt.

Karina had already produced a Headroom-only accuracy curve on LoCoMo:

| Compression | Accuracy |
|---:|---:|
| 0% (baseline) | 88% |
| 67% | 71% |
| 84% | 58% |
| 92% | 43% |

Plus a parameter sensitivity analysis. The missing piece was **cross-arm**: how does Headroom stack up against provider-native compaction and a custom summary prompt at matched compression ratios?

Additional context from the Slack discussion that framed the evaluation:

- `/stats` from Headroom's proxy (1,682 requests over several days): ~152 ms average optimization overhead, ~57% token savings, ~$252 cost savings.
- Overhead scales with context size: <1 ms for tiny passthrough, ~70 ms for <15k tokens, **15–23 s on 87–90k-token requests**. One outlier hit 37 s optimization on a 37k-token request.
- Operator verdict: the overhead is unattractive for real-time interactive usage but potentially valuable for async / batch workloads. Quality had only been assessed anecdotally — the formal quality-retention evaluation is what RES-333 is for.

## 3. Pivot 1 — the dataset gate

After Step 0 was scaffolded, a self-review flagged a hidden assumption: **provider-native compaction only fires above a token threshold**. If the dataset is too short, compaction arms become silent no-ops and the experiment produces nothing. A hard gate was added: **p50 ≥ 20k tokens** on the trajectory being benchmarked, to guarantee the smallest compaction threshold (25k) fires on at least half of cases.

Measured across candidates using `tiktoken cl100k_base`, streaming everything via `HfFileSystem`:

| Dataset | Slice | min | p50 | p90 | max | Gate |
|---|---|---:|---:|---:|---:|:---:|
| Nemotron `interactive_agent` | full trajectory | 2,997 | **3,615** | 4,328 | 6,367 | ❌ |
| Nemotron `tool_calling` | full trajectory | 268 | **3,924** | 7,694 | 16,612 | ❌ |
| LoCoMo | per session | 299 | 623 | 955 | 1,378 | ❌ (way under) |
| LoCoMo | full conversation (29 sessions concat) | 11,074 | **19,428** | 21,311 | 21,371 | ❌ (572 short) |
| **LongMemEval `s_cleaned`** | haystack per question | 100,115 | **103,953** | 105,714 | 105,874 | ✅ **5×** |

### What this told us

1. **Nemotron-Agentic-v1 is short agent demos, not long context.** Even the largest `tool_calling` trajectory (16.6k) is below our smallest compaction threshold. Useless as a comparison surface. Loader stays in repo; dataset deprecated for this experiment.
2. **LoCoMo is borderline-but-fails.** Natural conversation cluster is 19–21k. At Anthropic's *default* 100k compaction trigger, zero LoCoMo conversations fire. Forcing the trigger down to 15k is a 5× drop from the natural setting and makes the comparison artificial. N=10 also gives almost no statistical power.
3. **LongMemEval `s_cleaned` is the right surface.** 500 questions × 6 question types (multi-session 133, temporal-reasoning 133, knowledge-update 78, single-session-user 70, single-session-assistant 56, single-session-preference 30), ~48 haystack sessions per question, p50 ≈ 104k tokens. Decisively above the gate and literally what Bauke asked for in his RES-333 comment.

Live verification after the loader was built:

```
longmemeval_e47becba: 53 sessions, 529,220 chars context (≈ 132k tokens)
longmemeval_118b2229: 45 sessions, 522,643 chars context (≈ 130k tokens)
```

### Plan pivot

| Dataset | Role | Why |
|---|---|---|
| **LongMemEval `s_cleaned`** | **Primary** — all arms run here | Only candidate that decisively passes the gate; matches Bauke's literal ask; 500 Q across 6 types gives real statistical power |
| LongBench v1 suite | Phase 2 | LLMLingua-2 head-to-head for a follow-up blog; not on the critical path this week |
| LoCoMo | Appendix only | Karina's existing curve cited as supporting context, not re-run |
| Nemotron-Agentic-v1 | Deprecated | Loader kept as code pattern |

The compaction threshold sweep updated from `{25k, 50k, 100k}` (LoCoMo-sized) to `{50k, 75k, 100k}` (LongMemEval-sized). At LongMemEval's p50 ≈ 104k, Anthropic's default 100k trigger fires on most questions and 50k fires on essentially all of them.

### Known gap acknowledged, not closed

No "long context AND agentic" surface this week. Bauke's original framing wanted both. Nemotron failed the gate; τ-bench is unprobed; LongMemEval is long but not tool-use agentic. Explicitly flagged as a Phase 2 workstream — see §7.

## 4. Pivot 2 — provider compaction doesn't exist the way we assumed

After the runner build was complete, smoke tests against real APIs (total spend ~$5) surfaced architectural problems with both provider compaction arms and triggered a second design pivot. The findings are themselves a RES-333 deliverable.

### Smoke sequence

| # | Arm(s) | N | Result |
|---:|---|---:|---|
| 1 | baseline | 1 | ✅ Correct answer, 113k tokens, 6.9s |
| 2 | baseline + headroom + summary | 2 each | Headroom **56.4% compression**; summary_prompt silent no-op — **bug**: default `--model-context-window 200000` * `--trigger-fill 0.70` → fires at 140k, but haystacks are ~110k → trigger never fires. Fix: pass `--model-context-window 128000` |
| 3 | anthropic_compact | 1 | 15s, **wrong answer** (model said "no mention of any degree" when ground truth was clearly there and baseline had answered it correctly), `n_compactions=0` at threshold 70k, **negative compression ratio** (-20%) because dummy tool calls inflate tokens, original 7-chunk run **hung at 22 min** with `pydantic.ValidationError: read_history: chunk_id Missing required argument` (model calling dummy tools without arguments → SDK retrying in a tight loop) |
| 4 | 3-arm with adjusted params + judge | 2 each | Clean signal: baseline 50% / headroom 56.4% compression + 50% / summary 39.9% compression + 50% |
| 5 | openai_compact | 1 | **Architectural dead-end**: `400 Previous response with id 'resp_0e01...' not found` when using compacted response ID as `previous_response_id` |

### Direct API probe — what `responses.compact()` actually does

A 5-line probe against the real OpenAI API (`gpt-4o-mini`) revealed:

1. `responses.create(input="Remember: my favorite color is teal.")` → r1.id = `resp_0b88...`
2. `responses.compact(input="What is my favorite color?", previous_response_id=r1.id)` → `CompactedResponse` with `output = [user_msg, user_msg, compaction_item]`. **No assistant response in the output.** It is an inspection view of the compacted state, not a model call.
3. `responses.create(input="Tell me my favorite color.", previous_response_id=c2.id)` → **400 previous_response_not_found**
4. `responses.create(input="What is my favorite color?", previous_response_id=r1.id)` → works, returns `"Your favorite color is teal!"`

**Conclusion: `responses.compact()` is an analytics endpoint** returning a snapshot of how the conversation *would* be compacted. Its result ID is not chainable. There is no way to "compact and continue" a conversation through this API.

### What each provider actually ships

| Provider | Mechanism | Type | Works on LongMemEval? |
|---|---|---|---|
| Anthropic | `messages.create(context_management={edits: [clear_tool_uses_20250919, clear_thinking_20251015]})` | Lossy clear of tool-use or thinking blocks | **No-op** (no tool uses, no thinking turns) |
| Anthropic | `beta.messages.tool_runner(compaction_control={enabled: True, ...})` (in `anthropic/lib/tools/_beta_compaction_control.py`) | Client-side summarization — invokes the model with `DEFAULT_SUMMARY_PROMPT` and replaces history when cumulative tokens cross threshold | **Only fires inside tool_runner iterations**; forcing it onto a non-tool benchmark requires artificial dummy-tool scaffolding that distorts both tokens and model behavior (Smoke 3) |
| OpenAI | `responses.create(truncation="auto")` | Lossy first-N-tokens drop when input > window | Only fires when input > context window. With gpt-4o-mini's 128k and haystacks at ~104k, it **never fires** |
| OpenAI | `responses.compact()` | Inspection only — non-chainable snapshot | Not a compaction mechanism at all |

**Neither provider ships summarization-based compaction at the standard API level for non-tool-using benchmarks.** Bauke's framing on RES-333 ("openai compaction, anthropic compaction") was a reasonable assumption that doesn't match the actual API surfaces. This is a noteworthy finding for the report — it strengthens the case for Headroom + Feature A by showing they fill a real market gap.

### Second pivot

The headline experiment narrows from 5 arms to **3 honestly-comparable arms**:

1. **baseline** — uncompressed long context
2. **headroom_default** — Headroom's `ContentRouter` (adaptive compression)
3. **summary_prompt** — Feature A (Haiku 4.5 structured-output summarization at 55% fill)

Dropped arms — runner code stays in the repo as documented architectural dead-ends:

- ~~`anthropic_compact`~~ — excluded from headline; recoverable for a τ-bench follow-up in its native tool-calling habitat.
- ~~`openai_compact`~~ — kept as a documented inspection-API wrapper.

Total smoke spend: **~$5.30** across 5 runs. Prevented a $30+ "real run" that would have produced two arms of garbage.

### Baseline rate-limit artefact — important caveat

**All errors in the per-type sweeps are on the baseline arm, and all of them are Anthropic `429 rate_limit_error` responses (2M input tokens/minute org cap).** Headroom and summary_prompt have zero errors across all types. The per-type runs executed sequentially between Apr 9 00:37 and 00:41 and overlapped enough to burn through the per-minute TPM budget. Effective baseline sample sizes:

| Question type | baseline N (ok) | headroom N (ok) | summary N (ok) |
|---|---:|---:|---:|
| single-session-user (headline) | 50 | 50 | 50 |
| multi-session | 18 / 30 | 30 / 30 | 30 / 30 |
| temporal-reasoning | 26 / 30 | 30 / 30 | 30 / 30 |
| knowledge-update | 27 / 30 | 30 / 30 | 30 / 30 |
| single-session-assistant | 23 / 30 | 30 / 30 | 30 / 30 |
| single-session-preference | 20 / 30 | 30 / 30 | 30 / 30 |

**Implications:**

1. Reported baseline quality for each per-type run is computed over the **successfully-completed subset**, not all N=30. If the TPM errors are random with respect to case difficulty (expected, since they are throttling events), the Δ comparisons are unbiased in direction but slightly noisier than the nominal N suggests.
2. **The rate-limit errors are themselves a compression story.** Baseline sends the full ~110k-token haystack on every call; Headroom sends ~50k; summary_prompt sends ~65k. At the org-level TPM budget, compression is what lets the baseline-equivalent workload run concurrently at all. This is a real, separate operational argument in favour of shipping Headroom.
3. **Baseline's reported quality is probably slightly *over*-stated, not under-stated.** Multi-session and preference questions have the longest haystacks (more sessions per question), which correlates with both being hardest for baseline *and* most likely to throttle. The subset baseline managed to complete is plausibly the easier slice. This means the true Headroom Δ is **at least as large as reported**, very likely larger.
4. A clean Phase 2 rerun with explicit per-arm rate-limiting (or a slower serial schedule) would close the noise envelope.

### What this tells us

1. **Headroom generalises across 5 of 6 question types, with a grand-mean quality gain of +19.8pp at 55% compression and −42% latency.** The +22pp headline is not a single-type artifact. The largest win is `single-session-assistant` (+36.7pp, 93.3% absolute quality).
2. **`temporal-reasoning` is a wall for every arm.** Baseline and Headroom both collapse to 0%; summary_prompt scrapes 6.7%. Sonnet 4.5 at 110k context cannot do time arithmetic over haystack sessions. This is a model-level weakness, not a Headroom regression — but it means a compression layer is not a universal remedy.
3. **Feature A (`summary_prompt`) is weakly positive on average** (+6.3pp grand mean) but **dominated by Headroom on 5 of 6 types**. It posts positive deltas on 5 of 6 types (only `single-session-user` is negative, at −2pp) and is the only arm that clears 0 on temporal-reasoning (+6.7pp). The story is more nuanced than "strictly dominated — don't ship it": the schema matches some question types poorly, but the technique itself is not a dead end.
4. **Multi-session is the weakest type for Headroom** (+13.3pp over a 16.7% baseline). Cross-session reasoning may be a failure mode for lossless compression — cross-session anchors could be getting stripped. Worth a targeted ablation.

### Interpretation — "lost in the middle"

The headline +22pp is unsurprising once framed through the LongMemEval lens. The "lost in the middle" effect — LLMs losing attention on irrelevant tokens in long contexts — is well-documented for needle-in-haystack benchmarks. The LongMemEval paper itself notes that some memory systems beat *oracle* full-context retrieval by removing distractors. Headroom's `ContentRouter` + SmartCrusher relevance scoring does the same thing at the API-call layer that memory systems do at the store layer. 110k → ~50k = less haystack to lose your place in → better recall *and* lower latency.

The likely reason `summary_prompt` underperforms: its structured schema (`decisions / constraints / rejected_paths / file_refs / facts`) is shaped for software-engineering or planning workflows. Most LongMemEval `single-session-user` questions ask about casual conversational facts like "what degree did I graduate with" or "how long is my commute" that don't fit those categories. **The schema is the bug**, not the approach.

## 6. Caveats — what we are *not* claiming

1. **Single model.** Only Sonnet 4.5 on the answer side. The "lost in the middle" gradient varies by model; newer models with stronger long-context training may see smaller gains.
2. **Single benchmark family.** LongMemEval only. Coding, RAG retrieval, multi-agent shared memory all untested.
3. **Single Headroom config.** Only `headroom_default`. The parameter curve from Karina's LoCoMo work hasn't been re-traced on LongMemEval.
4. **Single scale.** N=50 on the headline; N=30 per additional type, but effective baseline N is reduced by rate-limit errors (see §5). Confidence intervals tightly fitted, not wide.
5. **Baseline rate-limit contamination.** Effective baseline N ranges from 18/30 (multi-session) to 27/30 (knowledge-update) due to Anthropic 429 throttling on full-haystack requests. Headroom and summary_prompt have 0 errors. See §5 for the full analysis — direction of the Δ is unbiased and very likely under-stated, but a clean rerun with explicit per-arm rate-limiting would tighten the noise envelope.
6. **No provider compaction baseline** — by design, once we confirmed the API surfaces don't support it for this benchmark class. τ-bench is the honest home for that comparison.
7. **Possible judge bias.** LLM-as-judge (Haiku 4.5) scores Haiku's own summaries via `summary_prompt`. Cross-judged or human-sampled scoring is a Phase 2 item.
8. **No orq production data.** Karina's reproduction found 0% compression on orq traces due to double-encoded JSON strings; we ran zero orq traces. The +22pp LongMemEval gain has not been shown to transfer to M&A due diligence workloads. See §7 workstream 1.

## 7. Recommendation

1. **Ship Headroom behind a feature flag for long-context memory / RAG workloads.** Data supports it across 5 of 6 LongMemEval question types at a single scale on a single model. Clear quality *and* latency win. Feature-flag gating gives us an exit if downstream telemetry surfaces regressions.
2. **Do not ship Feature A (`summary_prompt`) as-is.** It is dominated by Headroom on 5/6 types with the current schema. Keep the runner; re-evaluate with a question-type-appropriate schema (or free-form summaries) before ruling it out permanently.
3. **Open the "provider compaction is an analytics endpoint" finding with Bauke and the broader team.** It reframes the original RES-333 ask and strengthens the case that there is a real API-level gap a Headroom-like layer can fill.
4. **Do not over-generalize.** Before broader rollout, run Phase 2 across a second model and at least one agentic benchmark.

| Full | 0% | 88% | Baseline |

| 8k | **67%** | **71%** | Recommended max |
| 4k | 84% | 58% | Significant loss |
| 2k | 92% | 43% | Severe |
| 1k | 96% | 29% | Only recent survives |

**Key reproduction findings:**

- Parameters that matter most: `max_items_after_crush` (10–15 recommended), `min_ratio_relaxed/aggressive`, `model_limit`.
- Pipeline overhead 5–50 ms per span; LLM time saved (at ~0.05 ms/token for Sonnet) exceeds overhead by 2–10×.
- **orq-specific blocker:** orq tool outputs arrive as double-encoded JSON strings → `ContentRouter` gets 0% compression on them → a JSON string unwrapping layer before the router would unlock 30–44% compression. 57.5% of orq tool messages contain compressible nested arrays; 53% of tool content lives in those arrays.
- Priorities for orq.ai: (1) JSON unwrapping, (2) enable CCR for exact figure retrieval, (3) keep `max_items` at 10–15, (4) A/B accuracy tests on real agent outputs, (5) test coding & other workload types.

**Quality measurement.** Karina uses a regex/keyword match (`_answer_found`) — an answer is "preserved" if more than half of its significant words still appear in the compressed text. No LLM answer call, no LLM judge.

### 8.2 What we confirmed

| Reproduction finding | Our evidence |
|---|---|
| Headroom compression actually works (~55% on real workloads) | ✅ Matches — **54.3% on LongMemEval headline**, 54.7–55.8% stable across all 6 question types |
| Pipeline overhead is a net latency win | ✅ Stronger — p50 latency drops from **7.1 s (baseline) to 4.4 s (Headroom)** at ~110k tokens. −38%, replicates across every question type |
| Critical / high-information items are preserved | ✅ Matches — Headroom beat or matched baseline on 5 of 6 LongMemEval question types |
| The LoCoMo 67% compression / 71% accuracy anchor | ✅ Cited as-is; not re-run. Served as our starting reference for the N=50 design |
| Compression preserves answer findability on conversational data | ✅ Matches — `summary_prompt` is neutral on `single-session-user` (±2pp), Headroom is net positive |

### 8.3 What we learned differently (same direction, stronger claim)

#### 8.3.1 At long context, compression *improves* quality — it doesn't just preserve it

Karina's LoCoMo curve is monotonically decreasing: more compression → less accuracy. Every data point loses something versus the uncompressed baseline. Our LongMemEval numbers are **monotonically inverted at the 54% compression point** on 5 of 6 question types:

| Question type | baseline | headroom | Δ |
|---|---:|---:|---:|
| single-session-assistant | 56.7% | **93.3%** | **+36.7** |
| single-session-preference | 10.0% | 33.3% | +23.3 |
| knowledge-update | 46.7% | 70.0% | +23.3 |
| single-session-user | 52.0% | 74.0% | +22.0 |
| multi-session | 16.7% | 30.0% | +13.3 |
| temporal-reasoning | 0.0% | 0.0% | 0.0 |

**This doesn't contradict Karina — it extends her finding.** LoCoMo tops out at ~21k tokens (full conversation), which is why it failed our token-length gate in §3. At 21k tokens Sonnet 4.5 is comfortably inside its attention budget, so compression is a pure tradeoff. At ~110k tokens LongMemEval pushes past the "lost in the middle" threshold and removing distractors becomes a **net quality win**. The LongMemEval paper's own finding that some memory systems beat oracle full-context retrieval generalises directly to in-context compression once the haystack is long enough.

#### 8.3.2 Latency evidence scales up

Karina estimated LLM time saved at ~0.05 ms/token (from Sonnet's ~20k tok/s input throughput) and showed 5–50 ms pipeline overhead → 500–1,300 ms estimated LLM savings. We measured the real end-to-end wall-clock difference on actual API calls at ~110k tokens: **2,725 ms median savings per call** (7,100 ms → 4,375 ms). Roughly 2× her projected savings per call, which fits — her model was on conversations 5× smaller, and the "lost in the middle" model-time gradient is non-linear.

#### 8.3.3 "Temporal drops first" holds at scale — and gets worse

On LoCoMo, "Temporal" was the category that dropped first at low context limits. On LongMemEval at ~110k we see the terminal form of that failure: `temporal-reasoning` is 0% across **both** baseline *and* Headroom. It is not a compression problem; it is a Sonnet-4.5-at-long-context problem. Worth its own RES ticket — see §7, workstream 7.

#### 8.3.4 The "accuracy threshold" is question-type dependent

Karina's headline takeaway is "compress up to ~67% to keep accuracy ≥71%". That's a useful single number on LoCoMo. Our per-type breakdown shows the real shape is **per-question-type**: at a single 54% compression point, `single-session-assistant` gains +36.7pp while `multi-session` only gains +13.3pp. A single-number accuracy threshold undersells the interaction between compression and question semantics. The parameter defaults she recommends (`max_items` 10–15, `model_limit` matching the real model) are unchanged by our work.

### 8.4 What we learned that the reproduction doesn't cover

These are genuine new findings, not extensions.

#### 8.4.1 Provider compaction doesn't exist the way RES-333 assumed

Karina's reproduction is Headroom-only. We took RES-333's literal framing ("compare with openai compaction, anthropic compaction") and tried to build the comparison, which forced us to read both provider SDKs. The result is §4 of this report: neither provider ships summarization-based compaction at the standard API level for non-tool-using benchmarks. `anthropic_compact` only fires inside `tool_runner` loops; `openai responses.compact()` is an analytics/inspection endpoint whose result ID isn't chainable. This is itself a RES-333 deliverable and is not addressable through the reproduction's interactive surface.

#### 8.4.2 Summary-prompt is schema-shaped

Feature A (Haiku 4.5 structured summary with `decisions / constraints / rejected_paths / file_refs / facts`) was tested in parallel with Headroom. It achieves ~40% compression cleanly but is **dominated by Headroom on 5 of 6 types**. The identifiable root cause: the schema is shaped for SWE/planning workloads, not casual conversational recall ("what degree did I graduate with"). Karina's reproduction doesn't evaluate a summary-prompt alternative, so this is a new (negative) finding. Counter-nuance: Feature A is the only arm that clears 0% on temporal-reasoning (+6.7pp). A schema redesign for conversational tasks might flip the verdict.

#### 8.4.3 End-to-end LLM-judged quality vs keyword presence

This is the biggest methodological delta between the two efforts. Karina's `_answer_found` checks whether more than half of the answer string's significant words still appear in the compressed text. That measures **fact survival in the compressed representation**. It does not answer whether an LLM, given that compressed input, actually *produces* the right answer. We measure the latter: run Sonnet 4.5 on the compressed context and have Haiku 4.5 judge the output.

A compressed context can contain the answer terms but still fail to elicit the right response (model gets distracted by remaining distractors), or conversely lack the exact answer phrasing but still elicit a correct inference. These are different quantities and our numbers should not be directly plotted against Karina's LoCoMo curve.

#### 8.4.4 We have nothing on real orq traces — this is a gap

**This is the only gap the reproduction has and our work also has.** Karina found that orq's production tool outputs get **0% compression** because they're double-encoded JSON strings, and identified a JSON-string-unwrapping layer as the high-priority fix that would unlock 30–44% compression. We ran **zero** orq traces in compaction-compare. The +22pp quality gain on LongMemEval does *not* currently transfer to orq — we don't know whether, once unwrapping lands and orq JSON becomes compressible, the same "lost in the middle" quality-improvement effect would show up on M&A due diligence workloads. This is now Phase 2 workstream #1 — see §7.

### 8.5 What we did differently (methodology)

| Axis | Reproduction | compaction-compare |
|---|---|---|
| **Research question** | "Does Headroom's compression work and preserve quality on our workloads?" | "How does Headroom compare to provider compaction and a summary-prompt alternative at long context, end-to-end?" |
| **Arms** | Headroom only | baseline + `headroom_default` + `summary_prompt` (+ dropped `anthropic_compact`, `openai_compact`) |
| **Datasets** | LoCoMo (10 convs, 19–21k tokens), orq production (229 spans, 46–191k), README-scenario reproductions | LongMemEval `s_cleaned` (N=50 headline + N=30 × 5 per-type; ~110k haystack tokens; 6 question types) |
| **Dataset gate** | None | Added "p50 ≥ 20k tokens" gate after self-review; rejected LoCoMo and Nemotron for this reason |
| **Quality signal** | Keyword / regex fact survival in compressed text (`_answer_found`) | End-to-end: Sonnet 4.5 answers from compressed context, Haiku 4.5 LLM-as-judge scores the answer |
| **Latency signal** | Pipeline overhead measured; LLM time saved estimated at 0.05 ms/token | Measured wall-clock end-to-end latency on real API calls |
| **Infrastructure** | Streamlit UI around existing `headroom` package | New `CompactionCompareDriver` + CLI subcommand + 3 HF loaders + 5 arm runners + Δ-quality report renderer + 106 unit tests |
| **Cost** | In-app compression + occasional Claude analysis calls | ~$15 total (smokes + N=50 headline + 5 per-type sweeps) |
| **Deliverable shape** | Interactive HF Space for exploration | Markdown + JSON reports, branch with commits, this report |
| **Output artefact** | `orq/headroom_reproduction` HF Space (publishable) | `feat/compaction-compare` branch + `research/2026-04-09-res-333-report.md` (internal) |
| **LoCoMo's role** | Primary benchmark surface with the full sweep | Appendix only — Karina's curve cited as supporting context, not re-run |

### 8.6 Combined reading

- **Karina's reproduction** validates that Headroom's published claims hold on orq's own data, identifies the JSON-unwrapping fix as the highest-impact orq-specific unlock, and gives the team an interactive tool for exploring the parameter space.
- **compaction-compare** validates that Headroom wins against realistic alternatives at long context (where LoCoMo is too short to see it), surfaces the "compression *improves* quality past a context threshold" effect, and documents why provider-native compaction isn't a fair comparison baseline at the standard API level.
- **The single span between them** is Phase 2 workstream #1: re-run the 3-arm comparison on the 229-span orq dataset after the JSON-unwrapping fix lands.
