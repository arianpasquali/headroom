> ### ⚠ Erratum — §4 "Pivot 2" was wrong on BOTH provider sides
>
> The earlier draft of §4 concluded *"neither provider ships summarization-based compaction at the standard API level for non-tool-using benchmarks."* **That was wrong on both sides, for two different reasons, and is corrected below.**
>
> **1. Anthropic `compact_20260112`** — a first-class server-side compaction feature released **2026-01-12**, accessible via plain `beta.messages.create` with `betas=["compact-2026-01-12"]` and `context_management.edits=[{"type":"compact_20260112"}]`. Does **not** require tool calling. Models: **Opus 4.6 / Sonnet 4.6 / Mythos Preview — explicitly not Sonnet 4.5**, which is why an earlier Sonnet 4.5 probe saw nothing fire. Our installed SDK (`anthropic==0.76.0`) had no typed shapes for it; we upgraded to 0.92.0 and wrote `AnthropicCompactV2Runner` to get the actual head-to-head. Headroom beats it by +28pp on LongMemEval Sonnet 4.6 — see §5.1.
>
> **2. OpenAI Responses API context compaction** — the Apr 8 probe that concluded *"`responses.compact()` is an analytics endpoint"* was a **model-gating artefact** from probing on `gpt-4o-mini`, which is NOT in the supported-models list. The real feature surfaces as `responses.create(context_management={"type":"compaction","compact_threshold":N})` plus a standalone `POST /responses/compact`, supported on `gpt-5.3-codex` / `gpt-5.4` ([docs](https://developers.openai.com/api/docs/guides/compaction)). The compaction item **is** chainable when the right model is used. Wired up as `OpenAICompactV2Runner`, verified on `gpt-5.4` with a 2/2 N=2 smoke. Cross-provider head-to-head n≥20 run still pending as of this commit.
>
> **3. Anthropic session memory cookbook pattern** — a third client-side path: proactive background summarization via threading + prompt caching + a 6-section conversational schema, documented by Anthropic for long conversational apps. Our original `summary_prompt` arm is a naive synchronous un-cached version of this with the wrong schema.
>
> **Corrected framing.** Both vendors now ship server-side summarization compaction at the standard API level, on their latest models. This does **not** weaken the Headroom case — it strengthens a different, sharper claim:
>
> > *Headroom is the only cross-provider, transparent, question-aware, deterministic, inspectable context-compaction layer. Both vendors have now confirmed that context compaction is a real problem worth solving at the platform layer; Headroom is the one the user controls.*
>
> Semantic difference worth flagging: Anthropic's compaction block is a natural-language summary the caller can read, audit, or even edit; OpenAI's compaction item is **opaque and encrypted**, "not intended to be human-interpretable." For failure analysis and "what got dropped" reporting, Anthropic's output is introspectable while OpenAI's is not.
>
> Full context: [`research/2026-04-09-evaluation-plan-revision.md`](./2026-04-09-evaluation-plan-revision.md); cross-provider smoke findings and the load-bearing caveat that OpenAI's `compression_ratio` measures billable-token drift rather than actual context reduction: [`research/2026-04-09-streamlit-reproduction-comparison.md`](./2026-04-09-streamlit-reproduction-comparison.md) §4.1.b.
>
> **n=2 footnote rule.** Any comparative claim involving `openai_compact_v2` must be read with an "n=2 smoke" caveat until the n≥20 head-to-head run lands. The Anthropic side is N=50 and solid.

## TL;DR

- **On Sonnet 4.6, Headroom beats both the uncompressed baseline AND Anthropic's own shipped server-side compaction (`compact_20260112`) decisively on LongMemEval** `single-session-user` (N=50, ~125k-token haystacks):

  | arm | quality | Δ vs baseline | compression | p50 latency | cost / case |
  |---|---:|---:|---:|---:|---:|
  | baseline | 40.0% | — | 0% | 6,754 ms | $0.3756 |
  | **headroom_default** | **82.0%** | **+42.0pp** 🚀 | **54.2%** | **4,667 ms** | **$0.1727** |
  | anthropic_compact_20260112 | 54.0% | +14.0pp | 99.7% | 8,660 ms | $0.3792 |

  **+42pp vs baseline, +28pp vs Anthropic's shipped compaction, −31% latency, −54% cost per case.** Zero errors across all 150 runs. This is the corrected 3-arm Sonnet 4.6 headline after discovering `compact_20260112` (see erratum).

- **`compact_20260112` is not useless — it's just query-blind.** It genuinely helps vs uncompressed (+14pp) by compressing 125k tokens down to a ~350-token summary, but its prospective summarizer has to decide what to preserve before knowing the question, so it applies a generic salience prior that preserves identity-defining facts (degrees, jobs) and drops incidental-looking facts (commute times, phone numbers) even when the latter happen to be the later query target. **Headroom wins because its ContentRouter is query-aware at the compression step.**

- **Sonnet 4.6 baseline quality is *lower* than Sonnet 4.5 baseline on the same benchmark** (40.0% vs 52.0%). Counterintuitive but not a Headroom artifact — the model just loses more on uncompressed 125k-token haystacks, which makes compression more valuable, not less.

- **Sonnet 4.5 model ablation data (appendix, §5.2)** replicates the Headroom advantage shape across 6 LongMemEval question types. N=150 cross-type sweep: Headroom +20.0pp vs baseline at 54.8% compression, zero errors (with the rate-limit retry code). Per-type breakdown: single-session-user 78.6%, multi-session 32.3%, single-session-preference 22.2% — Headroom beats baseline on every type. Earlier 6-type grand means (N=30 per type, mixed rate-limit conditions) were Headroom +20.9pp, summary_prompt +5.2pp. The `temporal-reasoning` type is a wall for every arm at 0–7% regardless — a model-level weakness, not a compression problem. Clean temporal-reasoning rerun confirmed this at full N=30.

- **⚠ The original §4 "Pivot 2 — provider compaction doesn't exist" finding was wrong on BOTH provider sides.** Both Anthropic AND OpenAI now ship server-side summarization compaction at the standard API level, on their latest models:
  - **Anthropic `compact_20260112`** (released 2026-01-12, fires on plain `beta.messages.create` with a beta header, Sonnet 4.6 / Opus 4.6 / Mythos Preview only). Our SDK was too old to have typed shapes; we upgraded to 0.92.0 and ran the head-to-head — **Headroom beats it by +28pp on Sonnet 4.6 (§5.1).**
  - **OpenAI Responses API `context_management={"type":"compaction"}`** plus standalone `POST /responses/compact`, supported on `gpt-5.3-codex` / `gpt-5.4`. The Apr 8 "analytics endpoint" conclusion was a model-gating artefact from probing on `gpt-4o-mini` — the endpoint returns a degenerate response on unsupported models, but on `gpt-5.4` it produces a real (opaque, encrypted) compaction item that IS chainable. Wired up as `OpenAICompactV2Runner`, verified on `gpt-5.4` with a 2/2 N=2 smoke. Full n≥20 head-to-head still pending.
  - **Anthropic session memory cookbook pattern** — a third, client-side path for conversational apps. Our original `summary_prompt` arm is a naive synchronous un-cached version of it with the wrong schema.
  - **Reframed claim:** both vendors ship compaction on their latest models. Headroom is the only cross-provider, transparent, question-aware, deterministic, inspectable layer — and on the single benchmark we've tested head-to-head (LongMemEval single-session-user, Sonnet 4.6 N=50), it still wins decisively.

- **Recommendation (revised after the corrected headline AND the OpenAI correction):**
  1. **Ship Headroom behind a feature flag for long-context workloads on both OpenAI and Anthropic surfaces.** The Anthropic case is measured (§5.1); the OpenAI case is supported by a smoke-verified runner and the structural cross-provider-layer argument, with a proper n≥20 head-to-head as Phase 2 work.
  2. **Do not ship Feature A as-is.** The cookbook pattern is a better-shaped version of the same idea and should be re-evaluated in Phase 2 with a Sonnet summarizer (not Haiku).
  3. **Open the §4 correction with Bauke as the biggest new finding.** Both providers ship compaction — we tested one end-to-end at N=50 (Anthropic) and smoke-verified the other (OpenAI). Headroom still wins on the Anthropic head-to-head and is the only cross-provider option.
  4. **Phase 2 priorities (in order):** complete the Anthropic-vs-OpenAI n≥20 head-to-head on matched LongMemEval cases; complete the 4th arm (`anthropic_session_memory`) on Sonnet 4.6 with a Sonnet summarizer to close the cookbook-pattern measurement; re-run the comparison on orq production traces after Karina's JSON-unwrapping fix lands; τ-bench for the old `tool_runner(compaction_control)` comparison in its native habitat; Opus 4.6 as a second-model ablation; LongBench v1 + LLMLingua-2 for a publishable head-to-head.

## 1. Background

The Apr 7 sync assigned Headroom evaluation ownership to Arian with a one-week deadline. Bauke's literal ask on RES-333:

> Baseline: uncompressed long document (perhaps longmemeval + long context agentic dataset). Compare with: openai compaction, anthropic compaction, headroom compaction, custom summary prompt.

Karina had already produced a Headroom-only accuracy curve on LoCoMo:

| Compression | Accuracy |
|---:|---:|
| 0% (baseline) | 88% |
| 67% | 71% |
| 84% | 58% |
| 92% | 43% |

Plus a parameter sensitivity analysis. The missing piece was **cross-arm**: how does Headroom stack up against provider-native compaction and a custom summary prompt at matched compression ratios?

Additional context from the Slack discussion that framed the evaluation:

- `/stats` from Headroom's proxy (1,682 requests over several days): ~152 ms average optimization overhead, ~57% token savings, ~$252 cost savings.
- Overhead scales with context size: <1 ms for tiny passthrough, ~70 ms for <15k tokens, **15–23 s on 87–90k-token requests**. One outlier hit 37 s optimization on a 37k-token request.
- Operator verdict: the overhead is unattractive for real-time interactive usage but potentially valuable for async / batch workloads. Quality had only been assessed anecdotally — the formal quality-retention evaluation is what RES-333 is for.

## 3. Pivot 1 — the dataset gate

After Step 0 was scaffolded, a self-review flagged a hidden assumption: **provider-native compaction only fires above a token threshold**. If the dataset is too short, compaction arms become silent no-ops and the experiment produces nothing. A hard gate was added: **p50 ≥ 20k tokens** on the trajectory being benchmarked, to guarantee the smallest compaction threshold (25k) fires on at least half of cases.

Measured across candidates using `tiktoken cl100k_base`, streaming everything via `HfFileSystem`:

| Dataset | Slice | min | p50 | p90 | max | Gate |
|---|---|---:|---:|---:|---:|:---:|
| Nemotron `interactive_agent` | full trajectory | 2,997 | **3,615** | 4,328 | 6,367 | ❌ |
| Nemotron `tool_calling` | full trajectory | 268 | **3,924** | 7,694 | 16,612 | ❌ |
| LoCoMo | per session | 299 | 623 | 955 | 1,378 | ❌ (way under) |
| LoCoMo | full conversation (29 sessions concat) | 11,074 | **19,428** | 21,311 | 21,371 | ❌ (572 short) |
| **LongMemEval `s_cleaned`** | haystack per question | 100,115 | **103,953** | 105,714 | 105,874 | ✅ **5×** |

### What this told us

1. **Nemotron-Agentic-v1 is short agent demos, not long context.** Even the largest `tool_calling` trajectory (16.6k) is below our smallest compaction threshold. Useless as a comparison surface. Loader stays in repo; dataset deprecated for this experiment.
2. **LoCoMo is borderline-but-fails.** Natural conversation cluster is 19–21k. At Anthropic's *default* 100k compaction trigger, zero LoCoMo conversations fire. Forcing the trigger down to 15k is a 5× drop from the natural setting and makes the comparison artificial. N=10 also gives almost no statistical power.
3. **LongMemEval `s_cleaned` is the right surface.** 500 questions × 6 question types (multi-session 133, temporal-reasoning 133, knowledge-update 78, single-session-user 70, single-session-assistant 56, single-session-preference 30), ~48 haystack sessions per question, p50 ≈ 104k tokens. Decisively above the gate and literally what Bauke asked for in his RES-333 comment.

Live verification after the loader was built:

```
longmemeval_e47becba: 53 sessions, 529,220 chars context (≈ 132k tokens)
longmemeval_118b2229: 45 sessions, 522,643 chars context (≈ 130k tokens)
```

### Plan pivot

| Dataset | Role | Why |
|---|---|---|
| **LongMemEval `s_cleaned`** | **Primary** — all arms run here | Only candidate that decisively passes the gate; matches Bauke's literal ask; 500 Q across 6 types gives real statistical power |
| LongBench v1 suite | Phase 2 | LLMLingua-2 head-to-head for a follow-up blog; not on the critical path this week |
| LoCoMo | Appendix only | Karina's existing curve cited as supporting context, not re-run |
| Nemotron-Agentic-v1 | Deprecated | Loader kept as code pattern |

The compaction threshold sweep updated from `{25k, 50k, 100k}` (LoCoMo-sized) to `{50k, 75k, 100k}` (LongMemEval-sized). At LongMemEval's p50 ≈ 104k, Anthropic's default 100k trigger fires on most questions and 50k fires on essentially all of them.

### Known gap acknowledged, not closed

No "long context AND agentic" surface this week. Bauke's original framing wanted both. Nemotron failed the gate; τ-bench is unprobed; LongMemEval is long but not tool-use agentic. Explicitly flagged as a Phase 2 workstream — see §7.

> - **Anthropic `compact_20260112`** (released 2026-01-12) fires on plain `beta.messages.create` with a beta header, Sonnet 4.6 / Opus 4.6 / Mythos Preview only. We missed it because our installed SDK was too old (`anthropic==0.76.0`, no typed shapes) and I read the older deprecated `_beta_compaction_control.py` SDK path instead of the live docs. Upgraded to 0.92.0, wrote `AnthropicCompactV2Runner`, and ran the head-to-head in §5.1.

> - **Anthropic's session memory cookbook pattern** (client-side, proactive background summarization, prompt-caching optimized) — a third path. Our original `summary_prompt` runner is a naive synchronous un-cached version of it with a SWE/planning schema instead of the cookbook's conversational one.

> Full context in [`2026-04-09-evaluation-plan-revision.md`](./2026-04-09-evaluation-plan-revision.md) and [`2026-04-09-streamlit-reproduction-comparison.md`](./2026-04-09-streamlit-reproduction-comparison.md) §4.1.

### Direct API probe — what `responses.compact()` actually does

A 5-line probe against the real OpenAI API (`gpt-4o-mini`) revealed:

1. `responses.create(input="Remember: my favorite color is teal.")` → r1.id = `resp_0b88...`
2. `responses.compact(input="What is my favorite color?", previous_response_id=r1.id)` → `CompactedResponse` with `output = [user_msg, user_msg, compaction_item]`. **No assistant response in the output.** It is an inspection view of the compacted state, not a model call.
3. `responses.create(input="Tell me my favorite color.", previous_response_id=c2.id)` → **400 previous_response_not_found**
4. `responses.create(input="What is my favorite color?", previous_response_id=r1.id)` → works, returns `"Your favorite color is teal!"`

**Initial conclusion (Apr 8):** *"`responses.compact()` is an analytics endpoint. Result ID not chainable. No way to compact-and-continue through this API."* **This conclusion was wrong — it was a model-gating artefact.** See §4 correction below for the full story.

**Corrected overall conclusion.** **Both vendors ship server-side summarization compaction at the standard API level, on their latest models.** Anthropic ships one server-side primitive (A3) plus one recommended client-side pattern (A4); OpenAI ships one server-side primitive (O3/O4). The Apr 8 "nothing ships" finding was a combination of (a) SDK-version gating on the Anthropic side and (b) model gating on the OpenAI side — in both cases the mechanism exists and fires on the right model, and in both cases we missed it in the initial investigation.

**Reframed claim for Headroom's position.** The original draft's "market gap" narrative is wrong — both vendors are working on this space. The sharper, still-strong claim:

> **Headroom is the only cross-provider, transparent, question-aware, deterministic, inspectable context-compaction layer.** Both vendors have confirmed that context compaction is a real problem worth solving at the platform layer; Headroom is the one the user controls, the one that works identically across providers, and — on the single benchmark we've tested head-to-head at N=50 so far — the one that wins on quality, cost, and latency simultaneously.

**Semantic difference worth flagging for the sync.** Anthropic's compaction block is a natural-language summary the caller can read, audit, or even edit. OpenAI's compaction item is **opaque and encrypted**, "not intended to be human-interpretable." For failure analysis, auditability, and "what got dropped" reporting, Anthropic's output is introspectable while OpenAI's is not. Headroom's output is plain text, just like Anthropic's.

**Compression-metric caveat for the OpenAI arm.** `OpenAICompactV2Runner.compression_ratio` measures **billable-token drift**, not actual context reduction, because the Responses API compaction happens server-side and `usage.input_tokens` reflects what was billed (≈ 0.01 while `n_compactions == 1`). For `openai_compact_v2`, only `n_compactions`, `latency_ms`, and judge-scored quality are cross-comparable with other arms. The `compression_ratio` column for this arm should be footnoted as N/A in report tables. A follow-up measurement for the "real" compression number (at 2× cost per case via a paired-baseline diff) is Phase 2 work.

**Latency observation on `gpt-5.4` from the N=2 smoke.** The `openai_compact_v2` p50 ≈ 19.3s vs Sonnet baseline p50 ≈ 7.1s — meaningfully slower, not faster. This is a cost for the compaction work, not a benefit. Whether it holds at n≥20 is Phase 2.

### Direct API probes informing the corrected taxonomy

Two N=2 probes on Apr 9 against the real Anthropic API confirmed the feature's shape and surfaced its task-shape limitations.

**Probe 1 — `compact_20260112` with default settings (N=2):**

- Mechanism fires correctly on a 125k-token haystack at 60k input_tokens threshold.
- Response carries `['compaction', 'text']` content blocks and a `BetaUsage` object with a per-iteration `iterations` array (one `compaction` iter, one `message` iter).
- **Role-confusion failure mode:** The compaction summary wrote *"you graduated with a degree in Business Administration"* — correct about the user, but the final answer call parsed *"you"* as self-referential and rejected the summary as *"a previous conversation summary that contains inaccurate information. I'm Claude, I don't have a degree."* The compaction's output shape is designed for agent continuation ("you, the assistant, have been working on X"), not conversational fact recall about a human user.

**Probe 2 — `compact_20260112` with custom `instructions` and reframed system prompt (N=2):**

- Custom `instructions` forced third-person phrasing about "the user" in the compaction summary.
- Explicit system prompt disambiguated the pronoun reference: *"If you see a compaction block containing a summary, it describes facts the USER told you about themselves. It is not describing you."*
- **Case 1 fixed:** Compaction wrote *"According to our prior conversation, you graduated with a degree in Business Administration"*, and the final answer correctly returned the ground truth.
- **Case 2 not fixed:** The compaction summary said *"the user never mentioned anything about a daily commute"*, but the raw haystack verbatim contains *"i've been listening to audiobooks during my daily commute, which takes 45 minutes each way"* (tagged `has_answer: true`). The summarizer dropped the answer-bearing fact even though it was plainly present in the input.

**The case 2 failure is intrinsic to prospective summarization.** `compact_20260112` has to decide what to preserve *before* it knows the query. It applies a generic salience prior that preserves identity-defining facts (degrees, jobs, ages) but drops incidental-looking facts (commute times, favorite restaurants, phone numbers) — even when those incidental facts happen to be the later query target. **This is structurally different from Headroom**, which is query-aware and can retain distractor-shaped facts when they match the query.

**Probe 3 — session memory cookbook pattern (N=2):**

- Summary call with `cache_control: ephemeral` on the 125k-token haystack using the 6-section conversational schema and Haiku 4.5 as summarizer.
- `cache_creation_input_tokens=125,468`, `cache_read_input_tokens=0` on both cases. **Caching doesn't help in one-shot eval** — every case is a fresh haystack so we never get cross-case cache hits. The cookbook's ~80% cost saving claim is for running conversations with accumulated context, not for per-case benchmarks. Honest reading: the discount is real for its intended use case but doesn't transfer here.
- Summary latency: 8.7–18.9 s on Haiku. Answer latency (post-summary): 1.9–3.1 s. **Wall-clock and user-visible latencies diverge by ~5×**.
- **Case 1 correct** (summary cleanly captured "graduated with Business Administration"; answer returned it).
- **Case 2 failed** for a different reason than `compact_20260112`: Haiku 4.5 got meta-confused by the nested conversational framing and wrote *"The user is summarizing a prior conversation between themselves and an assistant"*, treating the input haystack as metadata about a summarization task. A cautionary data point for using small models on long nested inputs.

#### Headline result

| arm | n | compression | quality | **Δ vs baseline** | p50 latency | cost / case |
|---|---:|---:|---:|---:|---:|---:|
| baseline | 50 | 0% | 40.0% | — | 6,754 ms | $0.3756 |

#### 5.1.1 What just happened

Three observations jump out:

1. **The Headroom advantage is even larger on Sonnet 4.6 than on Sonnet 4.5.** On Sonnet 4.5 N=50 the same benchmark gave +22pp; on Sonnet 4.6 it's +42pp. The baseline itself is *worse* on Sonnet 4.6 (40.0% vs 52.0%) — Sonnet 4.6 appears to lose more on uncompressed 110k-token haystacks than Sonnet 4.5 did. Compressing away the distractors is more valuable for Sonnet 4.6, not less. This is consistent with the "lost in the middle" framing but counterintuitive if you'd expect newer models to be strictly better at long context.

2. **`compact_20260112` lives at a completely different operating point on the compression curve.** ~99.7% compression (reducing 125k haystacks to ~350 tokens of summary) vs Headroom's ~54%. That's not a fair apples-to-apples quality comparison — it's a head-to-head between "keep 46% of the tokens and let the model read them" (Headroom) and "throw away 99.7% of the tokens and make the model read a one-paragraph summary" (`compact_20260112`). **Both win +14pp or better over uncompressed**, which tells us both strategies help. Headroom's strategy helps more because it's query-aware: it knows which bits of the haystack might matter for the question and keeps them. `compact_20260112` is query-blind: it has to summarize prospectively, applying a generic salience prior that drops incidental-looking facts that may turn out to be the needle.

3. **Cost per case collapses for Headroom.** Baseline and `compact_20260112` both pay roughly full haystack input pricing per case (~$0.38) because both send 125k tokens to Sonnet 4.6 at input time — baseline as the conversation, `compact_20260112` as the thing to compact. Headroom sends only the compressed ~58k tokens, paying ~$0.17 per case (−54%). **At scale this is a meaningful line-item saving on top of the quality win.**

#### 5.1.2 Cross-referencing the N=2 smoke findings

The N=2 smoke probes from earlier in the day (§4) gave us enough signal on compact_20260112 to predict the role-confusion failure mode on default settings and to ship the runner with a reframed system prompt + custom `instructions`. Those fixes carried through to the N=50 run cleanly — zero errors, +14pp vs baseline. **The N=2 "case 2 / commute time" failure is the failure mode, not a one-off.** At 54.0% correct rate on N=50, the compact_v2 arm is getting approximately half the questions wrong, and from Probe 2 we know the failures are predominantly "incidental fact dropped during prospective summarization" rather than "reframing failed."

Headroom at 82.0% correct is preserving the needles because its ContentRouter is query-aware at the compression step — it knows the question when deciding what to keep. That's the structural advantage spelled out in §4.

#### 5.1.3 Why `anthropic_session_memory` isn't in the headline

The original plan included a fourth arm: `anthropic_session_memory`, implementing Anthropic's cookbook session memory pattern with Haiku 4.5 as the summarizer. An earlier 4-arm attempt **hung for 15+ minutes inside a single Haiku 4.5 summarization call** on a large haystack (~125k tokens) during the session_memory arm, and was killed without producing output. The runner itself works correctly (validated on N=2 smoke — see §4, Probe 3) but Haiku 4.5 on very long single-turn inputs is apparently prone to pathologically slow responses without a clean SDK timeout.

Rather than re-run with explicit per-call timeouts or a smaller `n`, we scoped the headline to the 3 arms that map most directly to Bauke's original RES-333 ask (baseline + provider compaction + Headroom) and characterized `anthropic_session_memory` qualitatively from the N=2 smoke data in §4. **Conclusions on `anthropic_session_memory`** from that smoke:

- Mechanism works; case 1 correct, case 2 wrong for a different reason than `compact_20260112` (Haiku meta-confusion rather than query-blind salience drop).
- Wall-clock latency is high (~10–22 s per case on Sonnet 4.6 + Haiku) but **user-visible latency** (modeling the cookbook's background-thread design) would be ~2–3 s.
- Cookbook's prompt caching discount doesn't transfer to one-shot per-case evaluation (every case has a fresh haystack; zero cache hits across cases).
- Haiku 4.5 appears undersized for nested conversational summarization on 125k-token inputs. A Sonnet-summarizer variant is worth trying in Phase 2.

**Full 4-arm characterization is Phase 2 workstream 0.5** (reduced scope, explicit per-call timeout, smaller N to start, or Sonnet summarizer swap).

### What this tells us

1. **Headroom generalises across 5 of 6 question types, with a grand-mean quality gain of +20.9pp at 55% compression and −39% latency.** The +22pp headline is not a single-type artifact. The largest win is `single-session-assistant` (+36.7pp, 93.3% absolute quality).
2. **`temporal-reasoning` is a wall for every arm.** The rerun confirms baseline=0.0% at full N=30. Headroom and summary_prompt hover at 0–7% and the 2/30 correct answers are stochastic — the arms flipped positions between runs. Sonnet 4.5 at 110k context cannot do time arithmetic over haystack sessions. This is a model-level weakness, not a Headroom regression, and a compression layer is not a universal remedy.
3. **Feature A (`summary_prompt`) is weakly positive on average** (+5.2pp grand mean) but **dominated or tied by Headroom on all 6 types**. Positive deltas on 4 of 6 types (−2pp on single-session-user, 0pp on temporal-reasoning, +3 to +13pp on the other four). The story is more nuanced than "strictly dominated — don't ship it": the schema matches some question types poorly, but the technique itself is not a dead end. A schema redesign for conversational tasks is the obvious next experiment.
4. **Multi-session is the weakest type for Headroom** (+13.3pp over a 16.7% baseline). Cross-session reasoning may be a failure mode for lossless compression — cross-session anchors could be getting stripped. Worth a targeted ablation.

### Interpretation — "lost in the middle"

The headline +22pp is unsurprising once framed through the LongMemEval lens. The "lost in the middle" effect — LLMs losing attention on irrelevant tokens in long contexts — is well-documented for needle-in-haystack benchmarks. The LongMemEval paper itself notes that some memory systems beat *oracle* full-context retrieval by removing distractors. Headroom's `ContentRouter` + SmartCrusher relevance scoring does the same thing at the API-call layer that memory systems do at the store layer. 110k → ~50k = less haystack to lose your place in → better recall *and* lower latency.

The likely reason `summary_prompt` underperforms: its structured schema (`decisions / constraints / rejected_paths / file_refs / facts`) is shaped for software-engineering or planning workflows. Most LongMemEval `single-session-user` questions ask about casual conversational facts like "what degree did I graduate with" or "how long is my commute" that don't fit those categories. **The schema is the bug**, not the approach.

## 6. Caveats — what we are *not* claiming

1. **Two models, limited coverage.** Sonnet 4.5 for the original 3-arm sweep; Sonnet 4.6 for the corrected 4-arm headline (required by `compact_20260112`, models supported: Opus 4.6 / Sonnet 4.6 / Mythos). The "lost in the middle" gradient varies by model; newer models with stronger long-context training may see smaller gains. Opus 4.6 as a second-model ablation is Phase 2 workstream #4.
2. **Single benchmark family.** LongMemEval only. Coding, RAG retrieval, multi-agent shared memory all untested. τ-bench is Phase 2 workstream #3.
3. **Single Headroom config.** Only `headroom_default`. The parameter curve from Karina's LoCoMo work hasn't been re-traced on LongMemEval.
4. **Single scale.** N=50 on the headline; N=30 per additional type. Confidence intervals tightly fitted, not wide.
5. **Baseline rate-limit contamination on 4 of 6 types in the Sonnet 4.5 sweep.** Effective baseline N ranges from 18/30 (multi-session) to 27/30 (knowledge-update) due to Anthropic 429 throttling on full-haystack requests. Headroom and summary_prompt have 0 errors. `temporal-reasoning` has been rerun clean (30/30 on all arms). The remaining 4 types should also be rerun with the rate-limit retry code before those Sonnet 4.5 numbers are treated as canonical — but now they're a model ablation appendix rather than the headline anyway. The Sonnet 4.6 rerun uses the rate-limit retry code from the start. See §5.3.
6. **No tool-loop compaction baseline** — `anthropic_compact` (`tool_runner(compaction_control)`) stays dropped from LongMemEval because forcing it onto a non-tool benchmark requires dummy-tool scaffolding that distorts behavior. τ-bench is the honest home.
7. **`compact_20260112` is task-shape-sensitive.** Probe 2 in §4 showed it can be coaxed into conversational fact-recall with the right `instructions` and system prompt, but it's still query-blind by design. On needle-in-haystack questions where the needle is an incidental detail (commute time, phone number, favorite restaurant), the summarizer's generic salience prior drops it. The headline numbers reflect that task-shape mismatch, not a mechanism failure — they're a fair benchmark of "what does this feature produce on this workload."
8. **Session memory caching discount doesn't transfer.** The cookbook's ~80% cost savings from `cache_control: ephemeral` don't materialize in one-shot per-case evaluation (every case has a fresh haystack). We pass caching flags faithfully because the cookbook says to, but the reported cost per case reflects full input pricing. A running-conversation benchmark would be needed to measure the cookbook's caching story honestly.
9. **`user_visible_latency_ms` is an idealized upper bound for `anthropic_session_memory`.** In production the cookbook pattern runs summarization on a background thread, so users only wait for the answer call. Our measurement assumes the summary was pre-computed — a favourable assumption for the cookbook arm, not a neutral measurement. Wall-clock latency tells the "synchronous worst case" story; user-visible tells the "proactive-background best case" story. Report both.
10. **Possible judge bias.** LLM-as-judge (Haiku 4.5) scores Haiku's own summaries via `anthropic_session_memory`. Cross-judged or human-sampled scoring is a Phase 2 item.
11. **No orq production data.** Karina's reproduction found 0% compression on orq traces due to double-encoded JSON strings; we ran zero orq traces. The LongMemEval gain has not been shown to transfer to M&A due diligence workloads. See §7 workstream #2.

## 7. Recommendation

> **Updated 2026-04-09 after §4 correction AND the 3-arm Sonnet 4.6 headline (§5.1).** The "pending" version of this section from an earlier draft is now superseded — we have actual numbers and the data is decisively positive on Headroom.

1. **Ship Headroom behind a feature flag for long-context workloads on both OpenAI and Anthropic.** Previously I was cautious about Anthropic pending the 4-arm rerun; with the Sonnet 4.6 3-arm N=50 results in hand (Headroom +42pp vs baseline, +28pp vs `compact_20260112`, −31% latency, −54% cost per case), the data supports shipping on Anthropic too. The recommendation is no longer gated on Phase 2.
2. **On OpenAI long-context workloads**, no provider-native summarization compaction exists at the standard API level — ship Headroom unreservedly once telemetry is in place.
3. **On Anthropic long-context workloads**, Headroom decisively beats `compact_20260112` on the benchmark that matches Bauke's original RES-333 ask (conversational long-context recall on 125k-token haystacks). The natural ship story is "we tested Anthropic's own shipped feature side-by-side; Headroom wins on quality, cost, and latency simultaneously."
4. **Do not ship Feature A (`summary_prompt`) as-is.** The session memory cookbook pattern is a better-shaped version of the same idea. Phase 2 workstream 0.5 should complete `anthropic_session_memory` as the 4th arm on Sonnet 4.6 with a Sonnet summarizer (not Haiku — see §5.1.3) before making a final decision on summary-based compaction.
5. **Present the corrected §4 finding and the Sonnet 4.6 headline to the team as a package.** The original §4 "provider compaction doesn't exist" narrative was half-wrong for Anthropic; the corrected story is stronger, not weaker. Headroom and `compact_20260112` sit at **different operating points on the compression curve** (~54% query-aware vs ~99.7% prospective summarization), and on LongMemEval-style conversational recall the query-aware point wins decisively. The interesting framing for the sync is "**two different tools for different shapes of context problem** — and on our workload the query-aware one wins."
6. **Do not over-generalize.** The Sonnet 4.6 result is one model, one question type (`single-session-user`), one benchmark. The Sonnet 4.5 N=150 ablation (§5.2) replicates the shape across three types, strengthening confidence. Phase 2 still matters: per-type sweep on Sonnet 4.6, Opus 4.6 as a second model, τ-bench for agentic workloads, orq production traces after JSON unwrapping. Don't claim "Headroom is better" in broad terms without those follow-ups.

## 8. Relationship to the HF Space reproduction (`orq/headroom_reproduction`)

Karina had already shipped a 5-page Streamlit reproduction of Headroom (HF Space: `orq/headroom_reproduction`) ahead of this work. The two efforts are **complementary and non-overlapping**. This section reconciles them so the team can read both as one coherent picture.

### 8.1 What the reproduction covers

Five pages, all Headroom-only (no cross-arm comparison):

1. **Headroom Benchmarks** — 1:1 reproduction of the README benchmarks: needle-in-haystack (100 logs, 1 CRITICAL error at pos 67 → checks for `PG-5523`), 4 workload scenarios (code search, SRE debugging, GitHub issue triage), plus the published accuracy table.
2. **Parameter Study** — interactive sweep across `max_items_after_crush`, `min_ratio_relaxed / aggressive`, `model_limit`, `bias`.
3. **orq Dataset** — 229 real orq.ai production traces (CaptainFresh M&A due diligence agent, 46–191k prompt tokens per span). Compression, cost projection, per-span latency, net-latency analysis (`tokens_saved × 0.05 ms/token − compression_overhead`), and a Claude-powered in-app explainer.
4. **LoCoMo Eval** — 10 long multi-session conversations (400–680 turns each). Context-window sweep `{1k, 2k, 4k, 8k, 16k, Full}`, QA accuracy by category (single-hop, temporal, multi-hop, open-ended, adversarial-excluded), semantic-diff "what was lost" view.
5. **Conclusion** — parameter recommendations, accuracy thresholds, latency tables, orq-specific architectural fix, priorities for orq.ai.

The headline LoCoMo curve from the reproduction:

| Context | Compression | QA accuracy | Verdict |
|---|---:|---:|---|
| Full | 0% | 88% | Baseline |
| 16k | 35% | 82% | Minimal loss |
| 8k | **67%** | **71%** | Recommended max |
| 4k | 84% | 58% | Significant loss |
| 2k | 92% | 43% | Severe |
| 1k | 96% | 29% | Only recent survives |

**Key reproduction findings:**

- Parameters that matter most: `max_items_after_crush` (10–15 recommended), `min_ratio_relaxed/aggressive`, `model_limit`.
- Pipeline overhead 5–50 ms per span; LLM time saved (at ~0.05 ms/token for Sonnet) exceeds overhead by 2–10×.
- **orq-specific blocker:** orq tool outputs arrive as double-encoded JSON strings → `ContentRouter` gets 0% compression on them → a JSON string unwrapping layer before the router would unlock 30–44% compression. 57.5% of orq tool messages contain compressible nested arrays; 53% of tool content lives in those arrays.
- Priorities for orq.ai: (1) JSON unwrapping, (2) enable CCR for exact figure retrieval, (3) keep `max_items` at 10–15, (4) A/B accuracy tests on real agent outputs, (5) test coding & other workload types.

**Quality measurement.** Karina uses a regex/keyword match (`_answer_found`) — an answer is "preserved" if more than half of its significant words still appear in the compressed text. No LLM answer call, no LLM judge.

### 8.3 What we learned differently (same direction, stronger claim)

#### 8.3.1 At long context, compression *improves* quality — it doesn't just preserve it

Karina's LoCoMo curve is monotonically decreasing: more compression → less accuracy. Every data point loses something versus the uncompressed baseline. Our LongMemEval numbers are **monotonically inverted at the 54% compression point** on 5 of 6 question types:

| Question type | baseline | headroom | Δ |
|---|---:|---:|---:|
| single-session-assistant | 56.7% | **93.3%** | **+36.7** |
| single-session-preference | 10.0% | 33.3% | +23.3 |
| knowledge-update | 46.7% | 70.0% | +23.3 |
| single-session-user | 52.0% | 74.0% | +22.0 |
| multi-session | 16.7% | 30.0% | +13.3 |
| temporal-reasoning (rerun) | 0.0% | 6.7% | +6.7 (noise) |

**This doesn't contradict Karina — it extends her finding.** LoCoMo tops out at ~21k tokens (full conversation), which is why it failed our token-length gate in §3. At 21k tokens Sonnet 4.5 is comfortably inside its attention budget, so compression is a pure tradeoff. At ~110k tokens LongMemEval pushes past the "lost in the middle" threshold and removing distractors becomes a **net quality win**. The LongMemEval paper's own finding that some memory systems beat oracle full-context retrieval generalises directly to in-context compression once the haystack is long enough. (Note: the temporal-reasoning +6.7pp is at the noise floor — see §5.3 — and neither Headroom nor summary_prompt actually helps on that type.)

#### 8.3.2 Latency evidence scales up

Karina estimated LLM time saved at ~0.05 ms/token (from Sonnet's ~20k tok/s input throughput) and showed 5–50 ms pipeline overhead → 500–1,300 ms estimated LLM savings. We measured the real end-to-end wall-clock difference on actual API calls at ~110k tokens: **2,725 ms median savings per call** (7,100 ms → 4,375 ms). Roughly 2× her projected savings per call, which fits — her model was on conversations 5× smaller, and the "lost in the middle" model-time gradient is non-linear.

#### 8.3.3 "Temporal drops first" holds at scale — and gets worse

On LoCoMo, "Temporal" was the category that dropped first at low context limits. On LongMemEval at ~110k we see the terminal form of that failure: `temporal-reasoning` is 0% across **both** baseline *and* Headroom. It is not a compression problem; it is a Sonnet-4.5-at-long-context problem. Worth its own RES ticket — see §7, workstream 7.

#### 8.3.4 The "accuracy threshold" is question-type dependent

Karina's headline takeaway is "compress up to ~67% to keep accuracy ≥71%". That's a useful single number on LoCoMo. Our per-type breakdown shows the real shape is **per-question-type**: at a single 54% compression point, `single-session-assistant` gains +36.7pp while `multi-session` only gains +13.3pp. A single-number accuracy threshold undersells the interaction between compression and question semantics. The parameter defaults she recommends (`max_items` 10–15, `model_limit` matching the real model) are unchanged by our work.

### 8.4 What we learned that the reproduction doesn't cover

These are genuine new findings, not extensions.

#### 8.4.1 Provider compaction doesn't exist the way RES-333 assumed

Karina's reproduction is Headroom-only. We took RES-333's literal framing ("compare with openai compaction, anthropic compaction") and tried to build the comparison, which forced us to read both provider SDKs. An earlier draft of this section concluded "neither provider ships summarization-based compaction at the standard API level for non-tool-using benchmarks" — that conclusion was **wrong on both sides** and is corrected in §4. Both Anthropic (`compact_20260112` on Sonnet/Opus 4.6) and OpenAI (Responses API `context_management={"type":"compaction"}` on `gpt-5.3-codex` / `gpt-5.4`) ship server-side summarization compaction at the standard API level on their latest models. The Apr 8 investigation missed Anthropic's feature because our SDK was too old and missed OpenAI's because we probed on a model that isn't in the supported-models list. Neither correction was addressable through the reproduction's interactive surface.

#### 8.4.2 Summary-prompt is schema-shaped

Feature A (Haiku 4.5 structured summary with `decisions / constraints / rejected_paths / file_refs / facts`) was tested in parallel with Headroom. It achieves ~40% compression cleanly but is **dominated or tied by Headroom on all 6 types**. The identifiable root cause: the schema is shaped for SWE/planning workloads, not casual conversational recall ("what degree did I graduate with"). Karina's reproduction doesn't evaluate a summary-prompt alternative, so this is a new (negative) finding. The technique is not a dead end — a schema redesign for conversational tasks is the obvious next experiment.

#### 8.4.3 End-to-end LLM-judged quality vs keyword presence

This is the biggest methodological delta between the two efforts. Karina's `_answer_found` checks whether more than half of the answer string's significant words still appear in the compressed text. That measures **fact survival in the compressed representation**. It does not answer whether an LLM, given that compressed input, actually *produces* the right answer. We measure the latter: run Sonnet 4.5 on the compressed context and have Haiku 4.5 judge the output.

A compressed context can contain the answer terms but still fail to elicit the right response (model gets distracted by remaining distractors), or conversely lack the exact answer phrasing but still elicit a correct inference. These are different quantities and our numbers should not be directly plotted against Karina's LoCoMo curve.

#### 8.4.4 We have nothing on real orq traces — this is a gap

**This is the only gap the reproduction has and our work also has.** Karina found that orq's production tool outputs get **0% compression** because they're double-encoded JSON strings, and identified a JSON-string-unwrapping layer as the high-priority fix that would unlock 30–44% compression. We ran **zero** orq traces in compaction-compare. The +22pp quality gain on LongMemEval does *not* currently transfer to orq — we don't know whether, once unwrapping lands and orq JSON becomes compressible, the same "lost in the middle" quality-improvement effect would show up on M&A due diligence workloads. This is now Phase 2 workstream #1 — see §7.

| Axis | Reproduction | compaction-compare |

### 8.6 Combined reading

- **Karina's reproduction** validates that Headroom's published claims hold on orq's own data, identifies the JSON-unwrapping fix as the highest-impact orq-specific unlock, and gives the team an interactive tool for exploring the parameter space.
- **compaction-compare** validates that Headroom wins against realistic alternatives at long context (where LoCoMo is too short to see it), surfaces the "compression *improves* quality past a context threshold" effect, and documents why provider-native compaction isn't a fair comparison baseline at the standard API level.
- **The single span between them** is Phase 2 workstream #1: re-run the 3-arm comparison on the 229-span orq dataset after the JSON-unwrapping fix lands.
