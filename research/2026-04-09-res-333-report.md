## TL;DR

- On **LongMemEval** (long-context memory benchmark, ~104k-token haystacks), **Headroom's default content router compresses the context by ~55% *and* improves end-to-end answer quality**. On the N=50 headline slice it beats the uncompressed baseline by **+22 percentage points** (74.0% vs 52.0%) while cutting p50 latency from 7.1s to 4.4s.
- The gain **generalises across 5 of 6 LongMemEval question types** (per-type N=30 sweep). Cross-type grand means: baseline 30.3% → **headroom_default 51.2% (+20.9pp)** → summary_prompt 35.6% (+5.2pp), at 55.1% / 39.5% compression and 5,586 ms / 9,393 ms p50 latency respectively. The one per-type exception is `temporal-reasoning`, where all arms collapse to 0–7% — a Sonnet 4.5 long-context weakness, not a Headroom problem. A clean rerun confirmed baseline=0.0% at full N=30 and showed the 2/30 "successes" are stochastic at the noise floor (original run: summary_prompt 6.7% / Headroom 0.0%; rerun: Headroom 6.7% / summary_prompt 0.0%).
- **All errors in the original sweep were Anthropic 429 rate-limit errors on the baseline arm** (baseline sends full ~110k-token haystacks → burns the 2M TPM org cap; Headroom and summary_prompt have zero errors). The rate-limit pattern is itself a compression story: at org-level TPM budgets, compression is what lets the workload run concurrently. A rerun with rate-limit retry code completed all three arms at full N=30 with zero errors — confirming baseline 0% on temporal-reasoning is real, not a reduced-N artifact.
- A custom summarization prompt ("Feature A" — Haiku 4.5 structured JSON) achieves ~40% compression with weakly-positive average quality (+5.2pp grand mean). It is **dominated or tied by Headroom on all 6 types** with its current SWE/planning schema. Not a dead end; a schema redesign for conversational tasks might flip the verdict.
- The RES-333 framing assumed that both OpenAI and Anthropic ship summarization-based compaction at the standard API level. **They don't.** The closest mechanisms are either lossy (`truncation="auto"`, `clear_tool_uses`), scoped to tool-calling loops (`tool_runner(compaction_control=...)`), or purely analytical (`responses.compact()` is an inspection endpoint whose result ID is not chainable). Both provider arms were dropped from the headline comparison after smoke runs exposed architectural dead-ends; this itself is a noteworthy finding — it strengthens the case that there is a real market gap for a Headroom-like compression layer.
- **Recommendation:** Ship Headroom behind a feature flag for long-context memory / RAG workloads. Do not ship Feature A as-is (schema-shaped for SWE/planning, not conversational recall). Open a Phase 2 workstream for (1) re-run on orq production traces after Karina's JSON-unwrapping fix lands, (2) a second model, (3) τ-bench (agentic tool-use), and (4) LongBench v1 (LLMLingua-2 head-to-head).

## 1. Background

The Apr 7 sync assigned Headroom evaluation ownership to Arian with a one-week deadline. Bauke's literal ask on RES-333:

> Baseline: uncompressed long document (perhaps longmemeval + long context agentic dataset). Compare with: openai compaction, anthropic compaction, headroom compaction, custom summary prompt.

Karina had already produced a Headroom-only accuracy curve on LoCoMo:

| Compression | Accuracy |
|---:|---:|
| 0% (baseline) | 88% |
| 67% | 71% |
| 84% | 58% |
| 92% | 43% |

Plus a parameter sensitivity analysis. The missing piece was **cross-arm**: how does Headroom stack up against provider-native compaction and a custom summary prompt at matched compression ratios?

Additional context from the Slack discussion that framed the evaluation:

- `/stats` from Headroom's proxy (1,682 requests over several days): ~152 ms average optimization overhead, ~57% token savings, ~$252 cost savings.
- Overhead scales with context size: <1 ms for tiny passthrough, ~70 ms for <15k tokens, **15–23 s on 87–90k-token requests**. One outlier hit 37 s optimization on a 37k-token request.
- Operator verdict: the overhead is unattractive for real-time interactive usage but potentially valuable for async / batch workloads. Quality had only been assessed anecdotally — the formal quality-retention evaluation is what RES-333 is for.

## 3. Pivot 1 — the dataset gate

After Step 0 was scaffolded, a self-review flagged a hidden assumption: **provider-native compaction only fires above a token threshold**. If the dataset is too short, compaction arms become silent no-ops and the experiment produces nothing. A hard gate was added: **p50 ≥ 20k tokens** on the trajectory being benchmarked, to guarantee the smallest compaction threshold (25k) fires on at least half of cases.

Measured across candidates using `tiktoken cl100k_base`, streaming everything via `HfFileSystem`:

| Dataset | Slice | min | p50 | p90 | max | Gate |
|---|---|---:|---:|---:|---:|:---:|
| Nemotron `interactive_agent` | full trajectory | 2,997 | **3,615** | 4,328 | 6,367 | ❌ |
| Nemotron `tool_calling` | full trajectory | 268 | **3,924** | 7,694 | 16,612 | ❌ |
| LoCoMo | per session | 299 | 623 | 955 | 1,378 | ❌ (way under) |
| LoCoMo | full conversation (29 sessions concat) | 11,074 | **19,428** | 21,311 | 21,371 | ❌ (572 short) |
| **LongMemEval `s_cleaned`** | haystack per question | 100,115 | **103,953** | 105,714 | 105,874 | ✅ **5×** |

### What this told us

1. **Nemotron-Agentic-v1 is short agent demos, not long context.** Even the largest `tool_calling` trajectory (16.6k) is below our smallest compaction threshold. Useless as a comparison surface. Loader stays in repo; dataset deprecated for this experiment.
2. **LoCoMo is borderline-but-fails.** Natural conversation cluster is 19–21k. At Anthropic's *default* 100k compaction trigger, zero LoCoMo conversations fire. Forcing the trigger down to 15k is a 5× drop from the natural setting and makes the comparison artificial. N=10 also gives almost no statistical power.
3. **LongMemEval `s_cleaned` is the right surface.** 500 questions × 6 question types (multi-session 133, temporal-reasoning 133, knowledge-update 78, single-session-user 70, single-session-assistant 56, single-session-preference 30), ~48 haystack sessions per question, p50 ≈ 104k tokens. Decisively above the gate and literally what Bauke asked for in his RES-333 comment.

Live verification after the loader was built:

```
longmemeval_e47becba: 53 sessions, 529,220 chars context (≈ 132k tokens)
longmemeval_118b2229: 45 sessions, 522,643 chars context (≈ 130k tokens)
```

### Plan pivot

| Dataset | Role | Why |
|---|---|---|
| **LongMemEval `s_cleaned`** | **Primary** — all arms run here | Only candidate that decisively passes the gate; matches Bauke's literal ask; 500 Q across 6 types gives real statistical power |
| LongBench v1 suite | Phase 2 | LLMLingua-2 head-to-head for a follow-up blog; not on the critical path this week |
| LoCoMo | Appendix only | Karina's existing curve cited as supporting context, not re-run |
| Nemotron-Agentic-v1 | Deprecated | Loader kept as code pattern |

The compaction threshold sweep updated from `{25k, 50k, 100k}` (LoCoMo-sized) to `{50k, 75k, 100k}` (LongMemEval-sized). At LongMemEval's p50 ≈ 104k, Anthropic's default 100k trigger fires on most questions and 50k fires on essentially all of them.

### Known gap acknowledged, not closed

No "long context AND agentic" surface this week. Bauke's original framing wanted both. Nemotron failed the gate; τ-bench is unprobed; LongMemEval is long but not tool-use agentic. Explicitly flagged as a Phase 2 workstream — see §7.

## 4. Pivot 2 — provider compaction landscape

> **Correction (2026-04-09):** An earlier draft of this section concluded "neither provider ships summarization-based compaction at the standard API level for non-tool-using benchmarks." **That is wrong for Anthropic as of 2026-01-12.** Anthropic shipped `compact_20260112`, a first-class server-side compaction feature accessible via plain `beta.messages.create`, three months before this work began. Our installed SDK (`anthropic==0.76.0`) had no typed shapes for it, and I extrapolated the "tool-loop-gated" finding from the older `_beta_compaction_control.py` SDK path without cross-checking the live docs. Full context in [`2026-04-09-evaluation-plan-revision.md`](./2026-04-09-evaluation-plan-revision.md).
>
> A third mechanism — Anthropic's **session memory cookbook pattern** (client-side, proactive background summarization, prompt-caching optimized) — was also missed. Our original `summary_prompt` runner is a naive synchronous un-cached version of it with a SWE/planning schema instead of the cookbook's conversational one.
>
> This section now documents the full picture: the original smoke runs that led us astray, the direct API probes that confirmed the OpenAI conclusions still hold, and the corrected Anthropic story.

After the original runner build, smoke tests against real APIs (total spend ~$5) surfaced architectural problems with the arms we knew about at the time and triggered a first design pivot. A second pivot came later, after Bauke pushed back on `summary_prompt` as a weak baseline and pointed at the live Anthropic docs.

### Direct API probe — what `responses.compact()` actually does

A 5-line probe against the real OpenAI API (`gpt-4o-mini`) revealed:

1. `responses.create(input="Remember: my favorite color is teal.")` → r1.id = `resp_0b88...`
2. `responses.compact(input="What is my favorite color?", previous_response_id=r1.id)` → `CompactedResponse` with `output = [user_msg, user_msg, compaction_item]`. **No assistant response in the output.** It is an inspection view of the compacted state, not a model call.
3. `responses.create(input="Tell me my favorite color.", previous_response_id=c2.id)` → **400 previous_response_not_found**
4. `responses.create(input="What is my favorite color?", previous_response_id=r1.id)` → works, returns `"Your favorite color is teal!"`

**Conclusion: `responses.compact()` is an analytics endpoint** returning a snapshot of how the conversation *would* be compacted. Its result ID is not chainable. There is no way to "compact and continue" a conversation through this API.

### What each provider actually ships — corrected taxonomy

Anthropic has **three** distinct compaction paths. OpenAI has one lossy mechanism plus one analytics endpoint.

| # | Provider | Mechanism | Type | Works on LongMemEval? |
|---:|---|---|---|---|
| A1 | Anthropic | `messages.create(context_management={edits: [clear_tool_uses_20250919, clear_thinking_20251015]})` | Lossy clear of tool-use or thinking blocks | **No-op** (no tool uses, no thinking turns in haystacks) |
| A2 | Anthropic | `beta.messages.tool_runner(compaction_control={enabled: True, ...})` — old SDK helper in `anthropic/lib/tools/_beta_compaction_control.py`, **now deprecated** in the 0.92 SDK with a pointer to A3 | Client-side summarization — invokes the model with the old `DEFAULT_SUMMARY_PROMPT` and replaces history when cumulative tokens cross threshold | **Only fires inside tool_runner iterations.** Forcing it onto a non-tool benchmark requires artificial dummy-tool scaffolding that distorts both tokens and model behavior (Smoke 3 — the run that hung 22 minutes on pydantic validation errors) |
| **A3** | **Anthropic** | **`beta.messages.create(betas=["compact-2026-01-12"], context_management={"edits":[{"type":"compact_20260112","trigger":{"type":"input_tokens","value":60000}}]}, ...)`** — released **2026-01-12** | **Server-side automatic summarization compaction.** Fires on plain `messages.create`, no tool loop required. Default trigger 150k input tokens, minimum 50k. | ✅ **Yes.** Requires Sonnet 4.6 / Opus 4.6 / Mythos Preview — not Sonnet 4.5. Tested on N=2 smoke April 9; role-confusion issue with default prompt, fixed with custom `instructions` + reframed system prompt. |
| **A4** | **Anthropic** | **Session memory cookbook pattern** (client-side) — documented at https://platform.claude.com/cookbook/misc-session-memory-compaction | **Proactive background summarization** with prompt caching and a 6-section conversational schema. Summaries run on a background thread so users don't wait for them in production. | ✅ **Yes.** Tested on N=2 smoke April 9. Caching doesn't pay off in one-shot eval (every case has a fresh haystack) but the proactive design lets us measure a separate "user-visible" latency that excludes the summary work. |
| O1 | OpenAI | `responses.create(truncation="auto")` | Lossy first-N-tokens drop when input > window | Only fires when input > context window. With gpt-4o-mini's 128k and haystacks at ~104k, **never fires**. |
| O2 | OpenAI | `responses.compact()` | Inspection only — non-chainable snapshot | Not a compaction mechanism at all. Direct 5-line API probe confirmed: `CompactedResponse.id` is non-chainable (`400 previous_response_not_found`). |

**Corrected overall conclusion.** Anthropic ships **two** usable summarization-based compaction paths for non-tool benchmarks (A3 as a feature, A4 as a documented pattern). OpenAI does **not**, by either mechanism. On LongMemEval the real comparison is Headroom vs A3 + A4; on tool-using benchmarks A2 (`tool_runner(compaction_control)`) becomes the relevant comparison in its natural habitat.

This reframes the "market gap" narrative that the original draft used. Headroom does fill a real gap on the OpenAI side, but on Anthropic the question is narrower: **is Headroom's query-aware retrieval-style compression at ~55% ratio materially better than Anthropic's prospective summarization-based compaction at ~99% ratio?** The two tools sit at different operating points on the compression curve, and the answer may be "they're for different workloads."

### Direct API probes informing the corrected taxonomy

Two N=2 probes on Apr 9 against the real Anthropic API confirmed the feature's shape and surfaced its task-shape limitations.

**Probe 1 — `compact_20260112` with default settings (N=2):**

- Mechanism fires correctly on a 125k-token haystack at 60k input_tokens threshold.
- Response carries `['compaction', 'text']` content blocks and a `BetaUsage` object with a per-iteration `iterations` array (one `compaction` iter, one `message` iter).
- **Role-confusion failure mode:** The compaction summary wrote *"you graduated with a degree in Business Administration"* — correct about the user, but the final answer call parsed *"you"* as self-referential and rejected the summary as *"a previous conversation summary that contains inaccurate information. I'm Claude, I don't have a degree."* The compaction's output shape is designed for agent continuation ("you, the assistant, have been working on X"), not conversational fact recall about a human user.

**Probe 2 — `compact_20260112` with custom `instructions` and reframed system prompt (N=2):**

- Custom `instructions` forced third-person phrasing about "the user" in the compaction summary.
- Explicit system prompt disambiguated the pronoun reference: *"If you see a compaction block containing a summary, it describes facts the USER told you about themselves. It is not describing you."*
- **Case 1 fixed:** Compaction wrote *"According to our prior conversation, you graduated with a degree in Business Administration"*, and the final answer correctly returned the ground truth.
- **Case 2 not fixed:** The compaction summary said *"the user never mentioned anything about a daily commute"*, but the raw haystack verbatim contains *"i've been listening to audiobooks during my daily commute, which takes 45 minutes each way"* (tagged `has_answer: true`). The summarizer dropped the answer-bearing fact even though it was plainly present in the input.

**The case 2 failure is intrinsic to prospective summarization.** `compact_20260112` has to decide what to preserve *before* it knows the query. It applies a generic salience prior that preserves identity-defining facts (degrees, jobs, ages) but drops incidental-looking facts (commute times, favorite restaurants, phone numbers) — even when those incidental facts happen to be the later query target. **This is structurally different from Headroom**, which is query-aware and can retain distractor-shaped facts when they match the query.

**Probe 3 — session memory cookbook pattern (N=2):**

- Summary call with `cache_control: ephemeral` on the 125k-token haystack using the 6-section conversational schema and Haiku 4.5 as summarizer.
- `cache_creation_input_tokens=125,468`, `cache_read_input_tokens=0` on both cases. **Caching doesn't help in one-shot eval** — every case is a fresh haystack so we never get cross-case cache hits. The cookbook's ~80% cost saving claim is for running conversations with accumulated context, not for per-case benchmarks. Honest reading: the discount is real for its intended use case but doesn't transfer here.
- Summary latency: 8.7–18.9 s on Haiku. Answer latency (post-summary): 1.9–3.1 s. **Wall-clock and user-visible latencies diverge by ~5×**.
- **Case 1 correct** (summary cleanly captured "graduated with Business Administration"; answer returned it).
- **Case 2 failed** for a different reason than `compact_20260112`: Haiku 4.5 got meta-confused by the nested conversational framing and wrote *"The user is summarizing a prior conversation between themselves and an assistant"*, treating the input haystack as metadata about a summarization task. A cautionary data point for using small models on long nested inputs.

### Second pivot — arms for the corrected headline

The corrected headline experiment runs on **Sonnet 4.6** (required by `compact_20260112`) with **four arms**:

1. **baseline** — uncompressed long context
2. **headroom_default** — Headroom's `ContentRouter` (query-aware, ~55% compression)

#### Temporal-reasoning rerun (Apr 9 13:46)

`temporal-reasoning` was rerun with the rate-limit retry code (`headroom/evals/runners/_rate_limit.py`, uncommitted at time of writing) to close the noise envelope on the most impactful type. The rerun completed all **30/30 cases on all three arms with zero errors**. It delivered two findings:

1. **Baseline 0% is real, not a reduced-N artifact.** The rerun confirmed Sonnet 4.5 correctly answers zero of 30 temporal-reasoning questions at ~110k context. This is *not* throttling or a partial sample — it is the model's actual performance on this question type at this context length. Sonnet 4.5 at 110k context cannot do time arithmetic over haystack sessions. Worth its own RES ticket.
2. **The 2/30 "success" on temporal-reasoning is stochastic.** In the original run, summary_prompt got 2/30 correct and Headroom got 0/30. In the rerun, **the positions flipped**: Headroom got 2/30 correct and summary_prompt got 0/30. Neither arm has a real signal on this question type; the 6.7% "delta" is noise at the single-correct-answer level. The canonical cross-type report now uses the rerun (Headroom 6.7% / summary_prompt 0.0%), but the honest reading is: **all three arms hover at the noise floor on temporal-reasoning, and neither compressed arm reliably beats baseline=0%.**

The rerun also **validated the rate-limit retry code** (zero 429s across 90 calls where the original run had 4 baseline errors on the same slice). That code is ready for a separate commit.

#### Implications for the per-type sweep at large

1. **The rate-limit errors are themselves a compression story.** Baseline sends the full ~110k-token haystack on every call; Headroom sends ~50k; summary_prompt sends ~65k. At the org-level TPM budget, compression is what lets the baseline-equivalent workload run concurrently at all. This is a real, separate operational argument in favour of shipping Headroom.
2. **Baseline's reported quality on the 4 non-rerun types is probably slightly *over*-stated, not under-stated.** Multi-session and preference questions have the longest haystacks (more sessions per question), which correlates with both being hardest for baseline *and* most likely to throttle. The subset baseline managed to complete is plausibly the easier slice. This means the true Headroom Δ is **at least as large as reported**, very likely larger.
3. **Phase 2 should rerun the remaining 4 question types** (multi-session, knowledge-update, single-session-assistant, single-session-preference) with the rate-limit retry code to close the noise envelope. Temporal-reasoning already has its clean rerun.

### What this tells us

1. **Headroom generalises across 5 of 6 question types, with a grand-mean quality gain of +20.9pp at 55% compression and −39% latency.** The +22pp headline is not a single-type artifact. The largest win is `single-session-assistant` (+36.7pp, 93.3% absolute quality).
2. **`temporal-reasoning` is a wall for every arm.** The rerun confirms baseline=0.0% at full N=30. Headroom and summary_prompt hover at 0–7% and the 2/30 correct answers are stochastic — the arms flipped positions between runs. Sonnet 4.5 at 110k context cannot do time arithmetic over haystack sessions. This is a model-level weakness, not a Headroom regression, and a compression layer is not a universal remedy.
3. **Feature A (`summary_prompt`) is weakly positive on average** (+5.2pp grand mean) but **dominated or tied by Headroom on all 6 types**. Positive deltas on 4 of 6 types (−2pp on single-session-user, 0pp on temporal-reasoning, +3 to +13pp on the other four). The story is more nuanced than "strictly dominated — don't ship it": the schema matches some question types poorly, but the technique itself is not a dead end. A schema redesign for conversational tasks is the obvious next experiment.
4. **Multi-session is the weakest type for Headroom** (+13.3pp over a 16.7% baseline). Cross-session reasoning may be a failure mode for lossless compression — cross-session anchors could be getting stripped. Worth a targeted ablation.

### Interpretation — "lost in the middle"

The headline +22pp is unsurprising once framed through the LongMemEval lens. The "lost in the middle" effect — LLMs losing attention on irrelevant tokens in long contexts — is well-documented for needle-in-haystack benchmarks. The LongMemEval paper itself notes that some memory systems beat *oracle* full-context retrieval by removing distractors. Headroom's `ContentRouter` + SmartCrusher relevance scoring does the same thing at the API-call layer that memory systems do at the store layer. 110k → ~50k = less haystack to lose your place in → better recall *and* lower latency.

The likely reason `summary_prompt` underperforms: its structured schema (`decisions / constraints / rejected_paths / file_refs / facts`) is shaped for software-engineering or planning workflows. Most LongMemEval `single-session-user` questions ask about casual conversational facts like "what degree did I graduate with" or "how long is my commute" that don't fit those categories. **The schema is the bug**, not the approach.

## 6. Caveats — what we are *not* claiming

1. **Single model.** Only Sonnet 4.5 on the answer side. The "lost in the middle" gradient varies by model; newer models with stronger long-context training may see smaller gains.
2. **Single benchmark family.** LongMemEval only. Coding, RAG retrieval, multi-agent shared memory all untested.
3. **Single Headroom config.** Only `headroom_default`. The parameter curve from Karina's LoCoMo work hasn't been re-traced on LongMemEval.
4. **Single scale.** N=50 on the headline; N=30 per additional type, but effective baseline N is reduced by rate-limit errors (see §5). Confidence intervals tightly fitted, not wide.
5. **Baseline rate-limit contamination on 4 of 6 types.** Effective baseline N ranges from 18/30 (multi-session) to 27/30 (knowledge-update) due to Anthropic 429 throttling on full-haystack requests. Headroom and summary_prompt have 0 errors. `temporal-reasoning` has been rerun clean (30/30 on all arms). The remaining 4 types should also be rerun with the rate-limit retry code before the results are treated as canonical. See §5.3 for the full analysis — direction of the Δ is unbiased and very likely under-stated.
6. **No provider compaction baseline** — by design, once we confirmed the API surfaces don't support it for this benchmark class. τ-bench is the honest home for that comparison.
7. **Possible judge bias.** LLM-as-judge (Haiku 4.5) scores Haiku's own summaries via `summary_prompt`. Cross-judged or human-sampled scoring is a Phase 2 item.
8. **No orq production data.** Karina's reproduction found 0% compression on orq traces due to double-encoded JSON strings; we ran zero orq traces. The +22pp LongMemEval gain has not been shown to transfer to M&A due diligence workloads. See §7 workstream 1.

## 7. Recommendation

1. **Ship Headroom behind a feature flag for long-context memory / RAG workloads.** Data supports it across 5 of 6 LongMemEval question types at a single scale on a single model. Clear quality *and* latency win. Feature-flag gating gives us an exit if downstream telemetry surfaces regressions.
2. **Do not ship Feature A (`summary_prompt`) as-is.** It is dominated by Headroom on 5/6 types with the current schema. Keep the runner; re-evaluate with a question-type-appropriate schema (or free-form summaries) before ruling it out permanently.
3. **Open the "provider compaction is an analytics endpoint" finding with Bauke and the broader team.** It reframes the original RES-333 ask and strengthens the case that there is a real API-level gap a Headroom-like layer can fill.
4. **Do not over-generalize.** Before broader rollout, run Phase 2 across a second model and at least one agentic benchmark.

## 8. Relationship to the HF Space reproduction (`orq/headroom_reproduction`)

Karina had already shipped a 5-page Streamlit reproduction of Headroom (HF Space: `orq/headroom_reproduction`) ahead of this work. The two efforts are **complementary and non-overlapping**. This section reconciles them so the team can read both as one coherent picture.

### 8.1 What the reproduction covers

Five pages, all Headroom-only (no cross-arm comparison):

1. **Headroom Benchmarks** — 1:1 reproduction of the README benchmarks: needle-in-haystack (100 logs, 1 CRITICAL error at pos 67 → checks for `PG-5523`), 4 workload scenarios (code search, SRE debugging, GitHub issue triage), plus the published accuracy table.
2. **Parameter Study** — interactive sweep across `max_items_after_crush`, `min_ratio_relaxed / aggressive`, `model_limit`, `bias`.
3. **orq Dataset** — 229 real orq.ai production traces (CaptainFresh M&A due diligence agent, 46–191k prompt tokens per span). Compression, cost projection, per-span latency, net-latency analysis (`tokens_saved × 0.05 ms/token − compression_overhead`), and a Claude-powered in-app explainer.
4. **LoCoMo Eval** — 10 long multi-session conversations (400–680 turns each). Context-window sweep `{1k, 2k, 4k, 8k, 16k, Full}`, QA accuracy by category (single-hop, temporal, multi-hop, open-ended, adversarial-excluded), semantic-diff "what was lost" view.
5. **Conclusion** — parameter recommendations, accuracy thresholds, latency tables, orq-specific architectural fix, priorities for orq.ai.

The headline LoCoMo curve from the reproduction:

| Context | Compression | QA accuracy | Verdict |
|---|---:|---:|---|
| Full | 0% | 88% | Baseline |
| 16k | 35% | 82% | Minimal loss |
| 8k | **67%** | **71%** | Recommended max |
| 4k | 84% | 58% | Significant loss |
| 2k | 92% | 43% | Severe |
| 1k | 96% | 29% | Only recent survives |

**Key reproduction findings:**

- Parameters that matter most: `max_items_after_crush` (10–15 recommended), `min_ratio_relaxed/aggressive`, `model_limit`.
- Pipeline overhead 5–50 ms per span; LLM time saved (at ~0.05 ms/token for Sonnet) exceeds overhead by 2–10×.
- **orq-specific blocker:** orq tool outputs arrive as double-encoded JSON strings → `ContentRouter` gets 0% compression on them → a JSON string unwrapping layer before the router would unlock 30–44% compression. 57.5% of orq tool messages contain compressible nested arrays; 53% of tool content lives in those arrays.
- Priorities for orq.ai: (1) JSON unwrapping, (2) enable CCR for exact figure retrieval, (3) keep `max_items` at 10–15, (4) A/B accuracy tests on real agent outputs, (5) test coding & other workload types.

**Quality measurement.** Karina uses a regex/keyword match (`_answer_found`) — an answer is "preserved" if more than half of its significant words still appear in the compressed text. No LLM answer call, no LLM judge.

### 8.3 What we learned differently (same direction, stronger claim)

#### 8.3.1 At long context, compression *improves* quality — it doesn't just preserve it

Karina's LoCoMo curve is monotonically decreasing: more compression → less accuracy. Every data point loses something versus the uncompressed baseline. Our LongMemEval numbers are **monotonically inverted at the 54% compression point** on 5 of 6 question types:

| Question type | baseline | headroom | Δ |
|---|---:|---:|---:|
| single-session-assistant | 56.7% | **93.3%** | **+36.7** |
| single-session-preference | 10.0% | 33.3% | +23.3 |
| knowledge-update | 46.7% | 70.0% | +23.3 |
| single-session-user | 52.0% | 74.0% | +22.0 |
| multi-session | 16.7% | 30.0% | +13.3 |
| temporal-reasoning (rerun) | 0.0% | 6.7% | +6.7 (noise) |

**This doesn't contradict Karina — it extends her finding.** LoCoMo tops out at ~21k tokens (full conversation), which is why it failed our token-length gate in §3. At 21k tokens Sonnet 4.5 is comfortably inside its attention budget, so compression is a pure tradeoff. At ~110k tokens LongMemEval pushes past the "lost in the middle" threshold and removing distractors becomes a **net quality win**. The LongMemEval paper's own finding that some memory systems beat oracle full-context retrieval generalises directly to in-context compression once the haystack is long enough. (Note: the temporal-reasoning +6.7pp is at the noise floor — see §5.3 — and neither Headroom nor summary_prompt actually helps on that type.)

#### 8.3.2 Latency evidence scales up

Karina estimated LLM time saved at ~0.05 ms/token (from Sonnet's ~20k tok/s input throughput) and showed 5–50 ms pipeline overhead → 500–1,300 ms estimated LLM savings. We measured the real end-to-end wall-clock difference on actual API calls at ~110k tokens: **2,725 ms median savings per call** (7,100 ms → 4,375 ms). Roughly 2× her projected savings per call, which fits — her model was on conversations 5× smaller, and the "lost in the middle" model-time gradient is non-linear.

#### 8.3.3 "Temporal drops first" holds at scale — and gets worse

On LoCoMo, "Temporal" was the category that dropped first at low context limits. On LongMemEval at ~110k we see the terminal form of that failure: `temporal-reasoning` is 0% across **both** baseline *and* Headroom. It is not a compression problem; it is a Sonnet-4.5-at-long-context problem. Worth its own RES ticket — see §7, workstream 7.

#### 8.3.4 The "accuracy threshold" is question-type dependent

Karina's headline takeaway is "compress up to ~67% to keep accuracy ≥71%". That's a useful single number on LoCoMo. Our per-type breakdown shows the real shape is **per-question-type**: at a single 54% compression point, `single-session-assistant` gains +36.7pp while `multi-session` only gains +13.3pp. A single-number accuracy threshold undersells the interaction between compression and question semantics. The parameter defaults she recommends (`max_items` 10–15, `model_limit` matching the real model) are unchanged by our work.

### 8.4 What we learned that the reproduction doesn't cover

These are genuine new findings, not extensions.

#### 8.4.1 Provider compaction doesn't exist the way RES-333 assumed

Karina's reproduction is Headroom-only. We took RES-333's literal framing ("compare with openai compaction, anthropic compaction") and tried to build the comparison, which forced us to read both provider SDKs. The result is §4 of this report: neither provider ships summarization-based compaction at the standard API level for non-tool-using benchmarks. `anthropic_compact` only fires inside `tool_runner` loops; `openai responses.compact()` is an analytics/inspection endpoint whose result ID isn't chainable. This is itself a RES-333 deliverable and is not addressable through the reproduction's interactive surface.

#### 8.4.2 Summary-prompt is schema-shaped

Feature A (Haiku 4.5 structured summary with `decisions / constraints / rejected_paths / file_refs / facts`) was tested in parallel with Headroom. It achieves ~40% compression cleanly but is **dominated or tied by Headroom on all 6 types**. The identifiable root cause: the schema is shaped for SWE/planning workloads, not casual conversational recall ("what degree did I graduate with"). Karina's reproduction doesn't evaluate a summary-prompt alternative, so this is a new (negative) finding. The technique is not a dead end — a schema redesign for conversational tasks is the obvious next experiment.

#### 8.4.3 End-to-end LLM-judged quality vs keyword presence

This is the biggest methodological delta between the two efforts. Karina's `_answer_found` checks whether more than half of the answer string's significant words still appear in the compressed text. That measures **fact survival in the compressed representation**. It does not answer whether an LLM, given that compressed input, actually *produces* the right answer. We measure the latter: run Sonnet 4.5 on the compressed context and have Haiku 4.5 judge the output.

A compressed context can contain the answer terms but still fail to elicit the right response (model gets distracted by remaining distractors), or conversely lack the exact answer phrasing but still elicit a correct inference. These are different quantities and our numbers should not be directly plotted against Karina's LoCoMo curve.

#### 8.4.4 We have nothing on real orq traces — this is a gap

**This is the only gap the reproduction has and our work also has.** Karina found that orq's production tool outputs get **0% compression** because they're double-encoded JSON strings, and identified a JSON-string-unwrapping layer as the high-priority fix that would unlock 30–44% compression. We ran **zero** orq traces in compaction-compare. The +22pp quality gain on LongMemEval does *not* currently transfer to orq — we don't know whether, once unwrapping lands and orq JSON becomes compressible, the same "lost in the middle" quality-improvement effect would show up on M&A due diligence workloads. This is now Phase 2 workstream #1 — see §7.

### 8.6 Combined reading

- **Karina's reproduction** validates that Headroom's published claims hold on orq's own data, identifies the JSON-unwrapping fix as the highest-impact orq-specific unlock, and gives the team an interactive tool for exploring the parameter space.
- **compaction-compare** validates that Headroom wins against realistic alternatives at long context (where LoCoMo is too short to see it), surfaces the "compression *improves* quality past a context threshold" effect, and documents why provider-native compaction isn't a fair comparison baseline at the standard API level.
- **The single span between them** is Phase 2 workstream #1: re-run the 3-arm comparison on the 229-span orq dataset after the JSON-unwrapping fix lands.
